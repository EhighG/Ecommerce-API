# k6 — 부하테스트 스크립트

## 담당 범위
- 담당하는 것: 실제 구매 흐름을 흉내 낸 부하·동시성 시나리오와 공용 라이브러리.
  - 주문·쿠폰 혼합 시나리오: `260519_order_bypass_auth/`, `260518_order_seperated_from_auth/`, `coupon/order-coupon-mixed.js`
  - 쿠폰 발급 동시성·중복: `coupon/`
  - 데이터 준비: `join-users*.js`, `register-products.js`, `add-cart-items.js`, `write-reviews.js`
  - 공용 라이브러리 `lib/`: `.env` 로딩, CSRF·로그인, 오류 본문 파싱, 후보 CSV 파싱
- 담당하지 않는 것:
  - 애플리케이션 코드
  - 후보 데이터를 뽑는 SQL(`../infra/sql`)
  - VM에서 자동 실행하는 스크립트(`../infra/scripts`)
  - 결과 분석 문서
- `data/`(계정, 후보 CSV)와 `.env`는 커밋하지 않는다. `test-result/`는 로컬 결과물이다.

## 항상 지켜야 할 것
- 필수 값은 `lib/env.js`의 `env(name)`으로 읽는다. 읽는 순서는 `__ENV` → `.env`(`K6_ENV_FILE`, 또는 관례 경로 순서대로)이고, 없으면 즉시 실패한다. `BASE_URL`은 `/api`까지 포함한다(예: `http://host:8081/api`).
- 인증 방식은 두 가지다.
  - **로그인 방식**(`lib/auth.js`): `GET /auth/csrf` → 로그인 → 상태 변경 요청에 CSRF 헤더. 403이면 토큰을 다시 받아 한 번 재시도한다(`requestWithCsrfRetry`).
  - **헤더 우회 방식**(`260519_order_bypass_auth`): `X-LoadTest-User-Id`, `X-LoadTest-Secret`. 대상 서버가 `loadtest` 프로필이고 우회가 켜져 있어야 한다. 실사용 서버를 대상으로 쓰지 않는다.
- 주문 생성 요청에는 반복(iteration)마다 새 `Idempotency-Key`를 넣어야 한다. 서버는 이 헤더가 없으면 400(`9100`)으로 거절한다.
  - 키를 재사용하면 서버가 기존 주문을 재응답하므로 처리량이 부풀려진다.
  - **현재 저장소의 어떤 스크립트도 이 헤더를 보내지 않는다**(코드 검색으로 확인). 멱등 처리를 도입하기 전에 작성된 스크립트들이라, 지금 서버를 대상으로 돌리면 주문 생성이 400으로 실패할 것으로 예상된다. 실행으로는 확인하지 않았다.
- 응답 형식을 파싱하는 코드는 서버 계약을 따른다. 오류 `code`는 **문자열**이다. 현재 `lib/auth.js`의 `readApiError`는 숫자만 인정해서, 오류 코드 체크가 모두 실패한다(수정 필요).

## 알아둘 구현 방식
- 시나리오 공통 구조:
  - 워밍업(기본 3분, 목표율의 절반) → 휴식(30초) → 측정 구간
  - 또는 `TEST_MODE=capacity`로 여러 부하율을 단계별로 실행
  - `CANCEL_RATIO`(기본 0.3) 비율로 주문항목을 취소하고 다시 조회한다
- 임계값 기본값: 주문 생성·취소 p99 1500ms, 상세 p99 500ms, 실패율 0.1%. 환경변수로 덮어쓸 수 있다.
- 후보 CSV는 주문 가능한 (사용자, 장바구니 항목, 쿠폰) 조합이다. 반복마다 다른 행을 써야 재고와 쿠폰이 겹치지 않는다. 테스트 전에 DB 상태에 맞게 다시 뽑는다.

## 테스트 기준
- 스크립트를 바꾸면 소량(`ORDER_RATE`를 낮게, `DURATION=30s`)으로 로컬 서버에 먼저 돌려 본다. 체크 실패율이 0인지 확인한다.
- 결과를 비교할 때는 워밍업 유무, 부하율, 구간, 데이터, 서버·DB 사양이 같은지 확인한다.
