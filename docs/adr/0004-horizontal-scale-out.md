# 0004. 동일한 API 인스턴스를 여러 대 두는 수평 확장, Redis 세션, 동시 실행해도 안전한 스케줄 작업

## 배경
주문 쿼리를 배치로 바꾼 뒤에도 같은 60 iter/s 조건에서 API VM CPU와 커넥션 획득 대기 병목이 남았다. 측정값은 [사례 3](../cases/03-horizontal-scale-out.md)에 있다.

목표는 60 iter/s를 안정적으로 처리하는 것이었다. 기준은 API별 p99 3초 미만, 실패율 1% 미만, 지표상 병목 없음이었다.

## 결정
- **같은 이미지의 API 인스턴스 2대 이상을 로드밸런서 뒤에 둔다**(GCE Managed Instance Group).
- **세션은 Redis(Spring Session)에 저장한다.** 어느 인스턴스로 요청이 가도 로그인 상태가 유지된다.
- **스케줄 작업은 모든 인스턴스에서 동시에 실행해도 결과가 같게 만든다.** 분산 락이나 별도 워커는 두지 않는다.
  - 쿠폰 캐시 적재: 조건부 초기화 스크립트로 한 번만 적재된다.
  - 조회수 반영: `SPOP` 청크로 인스턴스끼리 작업을 나눠 가진다. 원래는 상품 1건씩 처리했는데 청크 단위로 바꿨다.

결과: 60 iter/s에서 기준을 만족했고, 95 iter/s도 안정 처리했다(수치는 사례 3).

## 검토한 대안
- **단일 VM 스케일업**: 단일 장애점이 남는다. 스케일링을 무중단으로 하려면 결국 로드밸런서와 무상태 서버가 필요하다. 사양이 높아질수록 여러 대로 나누는 편이 더 세밀하게 확장할 수 있다.
- **서비스 분리(MSA)**: 분리 기준, 분산 트랜잭션, 서비스 간 통신 방식, 운영 복잡도를 새로 정해야 한다. 목표를 달성하지 못할 위험도 컸다. 서비스별 독립 확장이라는 장점은 지금 필요하지 않다.
- **세션을 로컬에 두고 sticky session**: 사용자마다 요청량이 달라 부하가 고르게 나뉘지 않는다. 인스턴스 하나가 죽으면 그 인스턴스의 세션이 사라진다.
- **JWT로 전환**: 장기적으로는 선택지지만 바꿀 것이 많다. 한다면 별도 작업으로 한다.
- **Memcached 등 다른 세션 저장소**: 이미 Redis를 쓰고 있고, Spring Session과 통합이 잘 되며, TTL 관리가 쉽다.
- **분산 락이나 전용 워커로 스케줄 작업 단일화**: 가용성이 낮아지고 신경 쓸 부분이 많다.

## 결과
- 인스턴스 메모리에 요청 사이의 공유 상태를 두면 안 된다. 새 스케줄 작업도 동시 실행을 전제로 설계해야 한다.
- Redis가 세션의 단일 장애점이다. Redis를 잃으면 모든 사용자가 다시 로그인해야 한다. 조회수 일부 유실도 허용한다.
- 조회 대상 상품이 많으면 조회수 반영이 늦어질 수 있다(1회 최대 청크 수 제한).
- 배포는 인스턴스 전체를 동시에 교체하므로 무중단이 아니다. 무중단 배포는 목표가 아니었다.
