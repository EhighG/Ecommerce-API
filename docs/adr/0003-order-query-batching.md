# 0003. 주문 생성의 재고 차감과 통계 증가를 JDBC 배치로 바꾸고, 주문항목 insert 배치와 비동기화는 하지 않는다

## 배경
주문 흐름 부하테스트(60 iter/s)에서 주문 생성 응답이 가장 느렸고, API VM CPU와 커넥션 풀 대기가 병목이었다. 측정값은 [사례 1](../cases/01-order-query-batching.md)에 있다.

주문 1건당 DB 호출이 많았고(상품 3개, 쿠폰 1장 기준), 이 가운데 재고와 통계의 상품별 단건 UPDATE가 큰 비중을 차지했다. 이 단건 UPDATE는 원래 데드락을 막으려고 도입한 것이었다. 풀 크기를 늘리는 방법은 검증해 보니 오히려 악화됐다.

## 결정
선택 기준은 네 가지였다: DB 호출 수 감소 우선, 주문 정합성 유지, JPA의 이점을 과하게 포기하지 않기, 수정 범위 최소화.
- 재고를 먼저 조회하던 단계를 없앴다. 대신 조건부 차감(`quantity >= ?`)을 JDBC 배치 한 번으로 실행한다(`product_id` 오름차순).
- `product_stat.order_item_count` 증가도 JDBC 배치로 바꿨다.
- JDBC URL에 `rewriteBatchedStatements=true`를 붙였다.

결과: DB 호출 수, 주문 생성 p95, 커넥션 획득 대기가 모두 줄었다(수치는 사례 1).

## 검토한 대안
- **주문항목 insert 배치**
  - `IDENTITY` 키에서는 Hibernate 배치가 되지 않는다.
  - 적용하려면 `Order` → `OrderItem` cascade를 포기하거나 ID 생성 전략을 바꿔야 한다. 그러면 주문항목 ID에 기대는 쿠폰 스냅샷 흐름도 연쇄적으로 바뀐다.
  - 앱에서 ID를 만드는 방식은 추가 문제가 있다. UUID는 CPU와 컬럼 크기 비용이 들고, 정수형은 다중 인스턴스 사이에서 충돌하지 않게 관리해야 한다.
  - 기대 효과에 비해 변경이 크다고 판단했다.
- **Outbox 등으로 일부 작업(통계 갱신 등) 비동기화**: Outbox insert가 추가로 필요해 DB 작업 수가 줄지 않는데, 일시적인 불일치를 허용할 수 있는 작업도 적어 기대 효과가 작다. 재고 차감은 강한 일관성이 필요해서 비동기화할 수 없다.
- **Hibernate batch update**
  - 재고는 조건부 UPDATE(`quantity >= ?`)로 차감하므로 엔티티 기반 Hibernate 배치를 적용하기 어렵다.
  - 통계는 Hibernate 배치로 더 간단히 만들 수 있지만, `product_stat` 엔티티를 먼저 조회해야 해서 DB 호출이 줄지 않는다.
- **재고 선조회 유지**: 재고가 부족한 상품은 보통 화면에서부터 걸러진다. 그래서 선조회로 실패를 미리 거르는 이득보다 매번 드는 조회 비용이 더 크다.
- **먼저 수평 확장**: DB에는 여유가 있고 API VM만 병목이어서 방향은 맞았다. 하지만 비효율을 먼저 줄인 다음에 확장해야 효과가 더 크다고 판단해 뒤로 미뤘다.

## 결과
- 재고와 통계 갱신은 영속성 컨텍스트를 거치지 않는다. 같은 트랜잭션에서 해당 엔티티를 읽으면 옛 값이 보인다.
- 배치 결과는 행마다 `== 1`인지 검사해야 한다. 검사를 빼면 재고 부족이 조용히 무시된다.
- 최대값 기준 병목(커넥션 대기, CPU)은 남았다. 이 문제는 수평 확장으로 해결했다([결정 기록 0004](0004-horizontal-scale-out.md)).
- 주문에서 파생되는 작업(알림, 정산 등)이 늘면 비동기화를 다시 검토한다.
