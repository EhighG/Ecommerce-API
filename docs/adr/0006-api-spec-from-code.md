# 0006. API 명세는 코드에서 생성해 커밋하고, 코드와 같은지를 테스트로 강제한다

## 배경
클라이언트용 계약은 `docs/contracts.md` 하나였다. 요청·응답 필드는 "DTO가 원본"이라며 적지 않아서, 클라이언트는 필드를 알려면 코드를 읽어야 했다. 엔드포인트별 오류도 손으로 쓴 표라 코드와 어긋나도 알 수 없었다. 클라이언트가 서버를 띄우지 않고도 필드와 분기할 오류를 모두 볼 수 있어야 했다.

## 결정
- springdoc-openapi로 컨트롤러와 DTO에서 OpenAPI 명세를 만들고, 그 결과를 `docs/api/openapi.yaml`에 커밋한다. GitHub Pages에 Swagger UI로 올려 서버 없이 본다.
- 엔드포인트별 정보는 코드에 둔다. 한 줄 설명은 `@Operation`, 분기할 오류는 `@ApiErrorCode`(조건만 적고 상태·코드·메시지는 `ErrorCode`에서 채움), 이름과 검증으로 드러나지 않는 필드 설명은 `@Schema`다.
- 테스트가 동기화를 강제한다. 생성한 명세와 커밋된 파일이 다르면 실패하고, 설명이나 오류 어노테이션이 없는 엔드포인트가 있으면 실패한다. PR 테스트 워크플로가 병합 전에 이 테스트를 돌린다.
- `contracts.md`에는 엔드포인트에 걸치는 계약(세션·CSRF 절차, 멱등 키, 오류 형식, 공통 오류 매핑)만 남긴다. 역할별 권한의 원본은 `SecurityConfig`, 소유자 검사는 `security.md`이고 명세에는 링크만 둔다.
- 실행 중인 서버에서는 `local` 프로필에서만 명세와 UI를 켠다.

## 검토한 대안
- **`contracts.md`에 필드까지 적고 동기화 규칙을 둠**: 도구는 늘지 않지만 DTO 필드를 손으로 옮겨 적게 된다. 어긋나도 잡아낼 수단이 없고, 문서가 천 줄 안팎으로 커진다.
- **Spring REST Docs**: 테스트가 통과해야 문서가 생겨 오류 응답까지 실제 동작과 같음이 보장된다. 하지만 웹 계층 테스트가 하나도 없어 엔드포인트 41개의 테스트를 새로 써야 하고, OpenAPI로 바꾸는 플러그인은 제3자 제품이다.
- **명세 파일을 직접 작성(design-first)**: DTO와 같은 사실을 두 곳에서 관리하게 된다.
- **명세를 커밋하지 않고 실행 중인 서버에서만 제공**: 서버가 떠 있지 않으면 아무도 볼 수 없다.

## 결과
- 컨트롤러나 요청·응답 DTO를 바꾸면 `./gradlew updateOpenApiSpec`으로 명세를 다시 만들어 함께 커밋해야 한다. 바뀐 명세는 PR diff로 드러난다.
- 오류 분기 목록이 실제로 던지는 예외와 같은지는 테스트로 검증하지 못한다. 빠짐없이 적었는지만 검사한다.
- 오류 응답 예시의 `message`는 `ErrorCode`의 기본 메시지다. 사용처에서 다른 문장을 넣으면 예시와 달라지므로, 명세 첫머리에 "예시이고 분기는 상태와 `code`로만 한다"고 적었다.
- 서버를 다시 배포하고 외부 클라이언트가 생기면 두 가지를 다시 정한다. 배포 프로필에서도 명세와 UI를 켤지, 그리고 Pages를 `develop` 대신 배포한 커밋 기준으로 올릴지다(`operations.md`의 "API 명세").
