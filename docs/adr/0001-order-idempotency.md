# 0001. 주문 생성은 멱등 키 기록으로, 주문항목 취소는 상태로 멱등성을 보장한다

## 배경
주문 생성과 주문항목 취소에는 재고, 쿠폰, 장바구니, 통계 변경이 함께 일어난다. 멱등 처리가 없을 때는 이런 문제가 있었다.
- 버튼을 두 번 누르거나 네트워크가 재시도하면 같은 주문이 두 건 생겼다.
- 실제로는 한 번 처리됐는데 두 번째 요청이 실패 응답을 받아 사용자가 혼란스러워했다.
- 이미 취소된 항목을 다시 취소하면 실패 응답이 나갔다.

## 결정
- **주문 생성**
  - 클라이언트가 보낸 `Idempotency-Key`로 논리 요청을 식별한다. 이 헤더는 필수다.
  - 기록은 `idempotency_record` 테이블에 둔다.
    - 유니크 범위는 `(user_id, scope, idempotency_key)`다.
    - 요청 지문(SHA-256)으로 같은 키에 다른 내용이 오는 경우를 가려낸다.
    - 상태는 `PROCESSING`(5분)과 `SUCCEEDED`(24시간) 두 가지이고, 만료되면 새로 선점할 수 있다.
  - 트랜잭션은 두 개로 나눈다.
    - 첫 번째: 선점 기록을 만들고 즉시 커밋한다.
    - 두 번째: 본 처리와 성공 표시를 한 트랜잭션에서 한다.
    - 실패하면 세 번째 트랜잭션에서 선점 기록을 지운다.
  - 멱등 로직은 기존 주문 서비스를 감싸는 래퍼 서비스(`IdempotentOrderPlacementService`)에 둔다.
- **주문항목 취소**: 별도 키 없이 대상 항목의 상태로 판단한다. 이미 `CANCELED`이면 성공으로 응답하고, 복구 작업은 하지 않는다.

## 검토한 대안
- **트랜잭션 하나로 처리(선점 + 본 처리 + 성공 표시)**: 선점 기록이 커밋되기 전에는 다른 요청이 볼 수 없다. 동시 요청이 "처리 중"인지 구분할 수 없고, 유니크 제약 위반에만 의존하게 된다.
- **트랜잭션 세 개로 모두 분리**: "본 처리는 성공했는데 성공 표시가 실패한" 상태를 따로 처리해야 한다. 그러면 재시도가 주문을 한 번 더 만들 위험이 생긴다.
- **유니크 범위를 키 하나로, 또는 사용자 + 키로**: 다른 사용자나 다른 API가 같은 키를 쓰면 잘못된 충돌이나 잘못된 재응답이 생긴다. 인덱스 키가 길어지는 비용은 감수했다.
- **AOP 기반 범용 멱등 처리**: 적용할 곳이 주문 생성 하나뿐이라 구현 비용이 크다. 멱등 처리는 요청마다 DB 호출을 늘리므로 무분별하게 적용하는 것도 피해야 한다. 적용 대상이 늘면 다시 검토한다.
- **기존 서비스에 직접 추가**: API 수준의 멱등 처리와 도메인 로직이 섞인다.
- **취소에도 멱등 키 사용**: 대상 자원이 이미 있으므로 상태만으로 충분히 판단할 수 있다. 키 기록의 DB 비용만 늘어난다.

## 결과
- 주문 생성 API는 `Idempotency-Key`가 없으면 400이다. 모든 클라이언트는 키를 만들어 관리해야 한다.
- 주문 생성 요청마다 DB 호출이 늘어난다(기록 조회·저장·갱신).
- 정리 트랜잭션이 실패하면 같은 키는 최대 5분 동안 409(`9103`)를 받는다.
- 멱등성 record는 24시간 뒤 만료된다. 그 뒤 같은 키를 보내면 새 주문으로 처리된다.
- 만료된 기록을 지우는 정리 작업은 없다. 같은 키가 다시 올 때만 지워지므로 테이블이 계속 커진다.
