# 엔지니어링 노트

## 함정과 해결

### 새 DB나 테스트 DB에서 키워드 검색이 500을 낸다
- **증상**: `GET /api/products?keyword=…`가 500(`9999`)을 내고, 로그에 FULLTEXT 인덱스를 찾을 수 없다는 SQL 오류가 남는다. 키워드가 없는 목록 조회는 정상이다.
- **원인**
  - 검색 쿼리는 `MATCH(name, description) AGAINST(? IN BOOLEAN MODE)`를 쓴다. 그런데 이 인덱스는 엔티티 어노테이션에 없다. `api/db/schema.sql`로 만든 DB에만 있다.
  - `create-drop`으로 스키마를 만드는 테스트 DB나, 엔티티에서 만든 DB에는 인덱스가 없다.
- **해결**
  - 인덱스를 만든다: `ALTER TABLE product ADD FULLTEXT INDEX ft_product_name_description (name, description) WITH PARSER ngram;`
  - MySQL 서버를 `--ngram_token_size=2 --innodb_ft_enable_stopword=OFF`로 띄운다. 토큰 크기가 다르면 같은 검색어라도 결과가 달라진다.
  - 키워드 검색을 테스트하려면 테스트 준비 단계에서 이 DDL을 실행해야 한다.
- **확인**: `EXPLAIN`에서 `product` 접근 방식이 `fulltext`로 나오는지 본다.

### 주문 생성과 취소가 동시에 돌면 데드락이 난다
- **증상**: 부하 중에 `Deadlock found when trying to get lock` 오류가 나고 주문 요청이 500으로 실패한다.
- **원인**: 주문 생성과 취소가 `inventory`와 `product_stat` 행을 서로 다른 순서로 잠갔다. 또 한 트랜잭션 안에서 여러 상품을 임의 순서로 갱신했다.
- **해결**
  - 두 경로 모두 `inventory` → `product_stat` 순서로 잠근다.
  - 배치 갱신은 `product_id` 오름차순으로 정렬한다(`InventoryJdbcRepository`, `ProductStatJdbcRepository`).
  - 취소 경로도 재고 복구(행 잠금) 다음에 통계를 감소시킨다.
- **확인**: 주문·취소를 섞은 k6 시나리오를 돌리고 MySQL `SHOW ENGINE INNODB STATUS`의 LATEST DETECTED DEADLOCK이 새로 생기지 않는지 본다.

### 커넥션 대기가 쌓인다고 풀 크기를 늘리면 더 느려진다
- **증상**: HikariCP pending이 수백까지 쌓이고, 획득 대기가 1초를 넘는다.
- **원인**: 병목은 API VM의 CPU였다. 요청 하나가 DB를 많이 호출할수록 JPA·JDBC 처리 비용이 커진다.
  - 풀을 10에서 30으로 늘리자 CPU 경쟁이 더 심해져 주문 생성 p95가 4.88초에서 6.92초로 나빠졌다.
- **해결**: 요청당 DB 호출 수를 줄이는 쪽으로 대응했다.
  - 재고 선조회를 없애고, 재고 차감과 통계 증가를 JDBC 배치로 바꿨다(19회 → 14회).
  - 수평 확장했다.
- **확인**: 풀 크기를 바꾸기 전에 같은 시간대의 API VM CPU 사용률과 Tomcat busy thread를 먼저 본다.

### JDBC 배치가 운영과 테스트에서 다르게 동작한다
- **증상**: 테스트에서는 괜찮은데 운영 성능이 다르게 나오거나, 그 반대다.
- **원인**
  - 운영 JDBC URL에는 `rewriteBatchedStatements=true`가 붙어 있어서, 배치가 DB 왕복 한 번으로 묶인다.
  - Testcontainers가 만드는 테스트 URL에는 이 옵션이 없다.
  - 또 `hibernate.jdbc.batch_size` / `order_updates` 설정은 `local`과 `dev` 프로필에만 있고 `loadtest` 프로필에는 없다.
- **해결**
  - JDBC URL 옵션을 지우지 않는다.
  - Hibernate 배치 설정을 바꿀 때는 세 프로필 파일을 모두 확인한다.
  - 배치 결과 개수를 검사하는 로직(각 행 `== 1`)을 바꾸면 운영 옵션을 켠 상태로 검증한다.

### `IDENTITY` 키 엔티티는 Hibernate insert 배치가 되지 않는다
- **증상**: `batch_size`를 설정해도 주문항목 insert가 한 건씩 나간다.
- **원인**: `IDENTITY` 전략은 insert를 해야 ID를 알 수 있다. 그래서 Hibernate가 insert를 묶지 못한다.
- **대응**: 주문항목 insert 배치는 의도적으로 적용하지 않았다. 적용하려면 ID 전략을 바꾸거나 cascade를 포기해야 하고, 쿠폰 스냅샷 흐름도 연쇄적으로 바뀐다. 배치는 UPDATE(재고, 통계)에만 JDBC로 적용한다.

### JDBC·벌크 UPDATE 뒤에 엔티티 값이 옛 값이다
- **증상**: 같은 트랜잭션에서 재고를 차감한 뒤 `Inventory` 엔티티를 읽으면 차감 전 수량이 보인다.
- **원인**: `JdbcTemplate`과 `@Modifying` JPQL은 영속성 컨텍스트를 거치지 않는다.
- **대응**: 직접 UPDATE 뒤에 같은 트랜잭션에서 그 엔티티 값으로 판단하지 않는다. 꼭 필요하면 다시 조회하되, 1차 캐시를 비우고 조회해야 한다.

### 로컬에서 GCP 자격 증명 오류로 서버가 뜨지 않는다
- **증상**: 기동할 때 `GcsConfig`에서 Application Default Credentials를 찾을 수 없다는 예외가 난다.
- **원인**
  - GCS 클라이언트 빈을 기동 시점에 만들기 때문에, 이미지 기능을 쓰지 않더라도 자격 증명이 있어야 한다.
  - `application-secret.yaml`에 적은 `GOOGLE_APPLICATION_CREDENTIALS`는 Spring 설정 값일 뿐이다. Google 라이브러리는 OS 환경변수나 gcloud 기본 자격 증명만 읽는다.
- **해결**: 실행 환경에 OS 환경변수 `GOOGLE_APPLICATION_CREDENTIALS=<키 파일 경로>`를 설정한다(IDE 실행 구성 포함). 또는 `gcloud auth application-default login`을 실행한다.

### 세션에 저장되는 클래스를 바꾸면 배포 직후 기존 로그인이 깨진다
- **증상**: 배포한 뒤 기존 사용자의 요청이 역직렬화 오류로 실패하거나 강제로 로그아웃된다.
- **원인**: Spring Session은 `CustomUserDetails`를 포함한 보안 컨텍스트를 Java 직렬화로 Redis에 저장한다(`serialVersionUID = 1L`).
- **대응**: 이 클래스의 필드를 바꾸는 배포는 전원 재로그인을 감수해야 한다. 필요하면 배포하면서 `ecommerce:session*` 키를 비운다.

### Redis를 잃거나 과거 상태로 되살아났을 때 쿠폰 발급
- **증상**: Redis를 재시작한 직후 열린 이벤트인데도 발급이 400(`7503`)으로 거절된다.
- **원인과 복구**
  - 쿠폰 발급은 Redis의 이벤트 캐시가 있어야만 진행된다.
  - 30초 주기 스케줄러가 캐시를 다시 올린다. 이때 남은 수량은 `초기 수량 − DB의 발급 건수`로 다시 계산하고, 발급자 집합은 비운다.
  - 그래서 이미 받은 사람이 다시 요청하면 Redis 단계는 통과하고, DB 유니크 제약에 걸려 보상(수량 복구) 후 400(`7506`)으로 끝난다. 남은 수량이 0이면 Redis 단계에서 400(`7507`)이다.
- **알아둘 점**
  - DB 유니크 제약은 1인 1장만 막는다. 수량 한도는 Redis만 판정한다. Redis가 비지 않고 과거 상태로 되살아나면(오래된 스냅샷, 복제 장애 조치) meta 키가 남아 재적재되지 않고, 실제보다 큰 수량으로 초과 발급될 수 있다(`docs/tracking/findings/coupon.md`).
  - 보상은 서비스 메서드 안에서 예외가 났을 때만 일어난다. DB 저장 후 커밋 단계에서 실패하거나, 보상하는 Redis 호출 자체가 실패하면 Redis 수량이 1 줄어든 채로 남는다. `saveAndFlush`로 제약 위반은 커밋 전에 드러나므로 드문 경우다.

### 조회수 반영 중 장애가 나면 일부 증가분이 사라진다
- **원인**
  - 반영 작업은 dirty set에서 상품 ID를 꺼내고(`SPOP`), 증가분을 읽어 지운 뒤(`GETDEL`), DB에 반영한다.
  - DB 반영이 예외로 실패하면 증가분을 되돌린다.
  - 하지만 꺼낸 뒤 반영 전에 프로세스가 죽으면 그 증가분이 사라진다.
  - 증가분 키만 남고 dirty set에서 빠진 상품은 다음 조회가 있을 때까지 반영되지 않는다.
- **대응**: 허용된 손실이다. 정확한 조회수가 필요해지면 이 구조 자체를 다시 설계해야 한다.

### 오류 `code`의 타입이 바뀐 것을 스크립트가 따라가지 못했다
- **증상**: k6 스크립트가 예상된 실패(재고 부족 `2501`, 쿠폰 소진 `7507` 등)를 예상 밖 실패로 집계하거나 첫 실패에서 멈춘다. 실패 로그의 `code`는 `none`으로 찍힌다.
- **원인**: 응답의 `code`는 문자열(`"9001"`)인데, `k6/lib/auth.js`의 `readApiError`는 숫자일 때만 오류 본문으로 인정했다. 스크립트의 기대 코드 상수도 숫자였다.
- **대응**: 응답 형식을 바꿀 때는 `k6/lib`의 파서와 스크립트의 기대 코드 상수를 같이 고친다.

### 환경변수를 빠뜨리면 빈 값이 아니라 `${…}` 문자열이 들어간다
- **증상**: `LOADTEST_AUTH_SECRET`을 설정하지 않았는데 부하테스트 우회가 켜진 채 서버가 뜬다. 또는 이미지 경로가 `${GCS_UPLOAD_PREFIX}/20260927/…`처럼 만들어진다.
- **원인**: Spring은 해석하지 못한 자리표시자를 오류로 보지 않고 문자열 그대로 `@ConfigurationProperties`에 넣는다. 그래서 "비어 있으면 실패" 검사를 통과한다.
- **대응**: 필수 설정은 값을 명시적으로 넣는다. 설정 클래스에서 빈 값과 함께 `${`로 시작하는 값도 거절하게 만드는 것이 안전하다.
- **확인**: 기능의 결과로 본다. 업로드 URL의 객체 경로 접두어가 기대한 값인지, 틀린 비밀값으로 우회 인증을 시도하면 401인지 확인한다.

### 로컬에서 만든 jar와 이미지에 비밀 설정이 들어간다
- **증상**: 로컬 `docker build` 결과 이미지나 `build/libs/*.jar` 안에 `application-secret.yaml`(DB·Redis 비밀번호 등)이 들어 있다.
- **원인**: 이 파일은 커밋되지 않지만 `src/main/resources` 안에 있다. `bootJar`는 리소스를 전부 포함하고, `Dockerfile`은 `src`를 통째로 복사한다. `.dockerignore`도 없다. 배포 워크플로의 빌드가 안전한 것은 저장소에 파일이 없기 때문일 뿐이다.
- **대응**: 로컬에서 만든 jar나 이미지는 외부로 내보내지 않는다. 배포 이미지는 배포 워크플로에서만 만든다.

### Redis가 죽으면 상품 상세 조회가 500이 된다
- **증상**: Redis 장애 중에 `GET /products/{id}`가 500(`9999`)을 낸다. 목록 조회는 정상이다.
- **원인**: 상세 조회가 조회수를 올리려고 Redis `INCR`을 호출하는데, 예외 처리가 없다. 조회수 손실은 허용하지만 조회 자체가 실패하는 것은 의도한 결과가 아니다. 로그인 세션도 Redis에 있어서, 장애 중에는 인증이 필요한 API도 실패한다.
- **대응**: 조회수 증가를 실패해도 조회가 계속되게 바꾸는 것은 별도 작업이다.

### 로그아웃 설정의 `deleteCookies("JSESSIONID")`는 아무 쿠키도 지우지 않는다
- **원인**: Spring Session을 쓰면 세션 쿠키 이름이 `SESSION`이다. 로그아웃이 동작하는 것은 세션 무효화 때문이다. Spring Session이 무효화된 세션의 쿠키를 만료시킨다.
- **대응**: 쿠키 이름에 기대는 코드(클라이언트, 테스트, 스크립트)를 만들지 않는다.

### 배포 워크플로의 테스트와 Docker 이미지 빌드가 서로 다른 Gradle을 쓴다
- **증상**: 배포 워크플로의 테스트 단계는 통과했는데 이미지 빌드에서만 실패할 수 있다(또는 그 반대).
- **원인**: 테스트 단계는 `./gradlew`(9.4.1)를 쓰고, `api/Dockerfile`은 `gradle:8.14.3` 이미지의 `gradle bootJar`를 쓴다. push나 PR에서 도는 자동 검사(CI)는 없고, 수동 배포 워크플로만 있다.
- **대응**: 빌드 스크립트나 플러그인 버전을 올릴 때는 `docker build`도 로컬에서 돌려 본다.

## 동작 방식 설명

- **멱등 기록은 트랜잭션 3개로 나뉜다.**
  - 선점 트랜잭션: 곧바로 커밋해서 동시 요청이 `PROCESSING` 기록을 볼 수 있게 한다.
  - 본 처리 + 성공 표시 트랜잭션: 한 트랜잭션이어야 "주문은 생겼는데 기록은 처리 중" 상태가 생기지 않는다.
  - 실패 정리 트랜잭션.
  - 정리에 실패하면 `PROCESSING` 기록이 남아서, 같은 키는 5분 동안 409(`9103`)를 받는다. 5분이 지나면 만료로 보고 새로 선점한다.
- **주문항목 조회의 판매자·썸네일은 스냅샷 값이다.** 판매자 기준 주문항목 조회(`oi.product.seller.id`)와 썸네일은 주문항목 테이블에 복사된 컬럼을 쓴다. 판매자가 닉네임을 바꾸거나 상품 이미지를 교체해도 과거 주문 화면은 바뀌지 않는다.
- **주문 상세는 fetch join 전용 조회를 쓴다.** `findDetailById`를 쓴다. `findById` 후 `getItemList()`로 바꾸면 추가 쿼리가 다시 생긴다.
- **리뷰 평점 통계는 UPDATE 한 문장으로 계산한다.** `rating_sum`, `review_count`, `rating_avg`를 한 문장에서 갱신하므로 동시 리뷰 작성에도 합계가 맞는다. 평균을 애플리케이션에서 계산해 저장하는 방식으로 바꾸면 동시성 문제가 생긴다.
  - **SET 절의 순서가 계산 결과를 바꾼다.** MySQL은 SET 대입을 왼쪽부터 차례로 적용하고, 뒤의 식은 앞에서 바뀐 값을 본다. 그래서 `addReview`와 `changeReviewRating`은 `rating_avg`를 **맨 앞에** 두어 갱신 전 합계와 개수로 계산한다. `rating_avg`를 다른 대입 뒤로 옮기면 평균이 조용히 틀어진다(테스트가 없어서 잡히지 않는다).

## 반복 작업 체크리스트

### 엔티티나 테이블을 바꿀 때
1. 엔티티를 수정하고, 같은 변경의 DDL(ALTER/CREATE)을 작성한다. `api/db/schema.sql`에도 같은 변경을 반영한다.
2. `./gradlew test`를 실행한다. 테스트는 `create-drop`이라 DDL 누락을 잡지 못한다.
3. 로컬 MySQL에 DDL을 적용하고 `local` 프로필로 기동한다. `validate`가 통과하면 매핑과 DDL이 일치한다는 뜻이다.
4. 새 테이블이면 `OrderServiceIntegrationTestSupport.CLEANUP_TABLES`에 추가한다. 정리할 때 FK 검사를 끄므로 순서는 상관없다. 빠뜨리면 테스트끼리 데이터가 섞인다.
5. 배포 전에 클라우드 DB에 같은 DDL을 적용한다. 적용하지 않고 배포하면 새 인스턴스가 기동하지 못하고, 전체 교체 방식이라 서비스가 멈춘다.

### API 엔드포인트를 추가할 때
1. `SecurityConfig`의 역할별 matcher 목록에 경로를 넣는다. 넣지 않으면 "로그인한 사용자 누구나"로 열린다.
2. 서비스에서 소유자를 검사하고, 404와 403 기준을 따른다.
3. 필요한 오류 코드를 `ErrorCode`의 도메인 대역에 추가한다.
4. `security.md` 인가 표에 행을 추가하고, `contracts.md` 엔드포인트 목록에 경로, 한 줄 설명, 클라이언트가 분기할 업무 오류를 추가한다. 요청·응답 필드는 DTO가 원본이라 적지 않는다.
5. 확인: 비로그인(401), 다른 역할(403), 다른 소유자(사용자 소유 자원은 404, 공개 자원은 403)로 호출해 본다.

### 스케줄 작업을 추가할 때
1. 인스턴스 2대가 같은 순간에 실행해도 결과가 같은지 먼저 설계한다(원자적 조건부 연산, `SPOP` 분배, 유니크 제약).
2. 실패하면 로그를 남기고 다음 주기에 다시 시도할 수 있게 한다. 예외가 스케줄러 스레드를 죽이면 안 된다.
3. 확인: 로컬에서 인스턴스 2대를 띄우고(`api/infra/scaleout-local/` 예시) 결과가 중복되지 않는지 본다.

### 부하테스트를 돌릴 때
1. 대상 서버를 `loadtest` 프로필, `LOADTEST_AUTH_ENABLED=true`, `LOADTEST_AUTH_SECRET`으로 띄운다.
2. 후보 데이터를 준비한다. `infra/sql/order_coupon_mixed_candidates_V3.sql`은 장바구니 항목과 새 쿠폰 이벤트·발급 쿠폰을 넣은 뒤 후보를 뽑는다(데이터 준비 + 후보 추출). 그래서 부하테스트 전용 DB에서만 돌린다. 자동 실행 스크립트가 대상 DB 확인(`loadtest_marker` 표)과 CSV 생성을 한다(`operations.md`).
3. 워밍업 구간(기본 3분)을 반드시 둔다. JVM 워밍업 없이 측정한 값은 비교에 쓰지 않는다.
4. 확인: 결과를 비교할 때는 부하율, 구간 구성, 데이터, DB 인스턴스 사양이 같은지 먼저 맞춘다. DB 인스턴스만 바꿔도 결과가 수십 배 달라진 적이 있다.
