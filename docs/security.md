# 보안 정책

## 보호 대상

| 자산 | 위협 | 현재 방어 |
|---|---|---|
| 사용자 계정(이메일·비밀번호) | 탈취, 무단 로그인 | BCrypt 해시 저장, 세션 인증 |
| 사용자 소유 자원(주문, 주문항목, 리뷰, 장바구니 항목, 발급 쿠폰, 업로드 이미지) | 남의 자원 조회·변경 | 서비스 계층의 소유자 검사. 실패하면 404로 존재 자체를 숨김 |
| 상품·재고 | 남의 상품 수정 | 판매자 일치 검사. 실패하면 403 |
| 재고·쿠폰·주문 정합성 | 중복 요청, 동시 요청 | 멱등 키, 조건부 차감, 낙관적 락, 유니크 제약 |
| 인프라 자격 증명(DB, Redis, GCP, 부하테스트 비밀값) | 저장소 유출 | 커밋 금지 파일, 환경변수 주입 |

## 인증 흐름

1. **CSRF 토큰 발급**: `GET /api/auth/csrf`를 호출하면 세션이 생기고(세션 쿠키 `SESSION`, Spring Session 기본 이름), 그 세션에 묶인 CSRF 토큰과 헤더 이름을 돌려준다.
2. **로그인**: `POST /api/auth/login`에 JSON `{email, password}`와 CSRF 헤더를 보낸다. 성공하면 1번에서 생긴 같은 세션이 인증 상태가 된다.
   - CSRF 토큰이 없거나 틀림 → 403. 애플리케이션 오류 형식(`code`/`message`)의 본문은 없다.
   - 본문을 JSON으로 읽을 수 없음 → 인증 실패로 처리해 401.
   - 이메일이나 비밀번호가 비어 있음 → 401.
   - 탈퇴한 사용자이거나 이메일이 없음 → 401. 둘을 구분하지 않는다. 없는 계정에도 비밀번호 비교를 해서 응답 시간으로도 구분되지 않게 한다.
   - 비밀번호 불일치 → 401.
   - 성공 → 200, 본문 없음. 인증 정보(사용자 ID, 이메일, 역할)를 세션에 저장한다.
3. **이후 요청**: 쿠키로 세션을 찾아 인증 정보를 복원한다. 세션은 Redis에 있으므로 어느 인스턴스로 가도 같다.
   - 세션이 없거나 만료됨 → 401, 본문 없음.
   - 상태를 바꾸는 요청(POST/PATCH/DELETE)은 CSRF 헤더가 필요하다. 없거나 틀리면 403.
4. **세션 종료**
   - 30분 동안 요청이 없으면 만료된다.
   - 로그아웃(`POST /api/auth/logout`)하면 그 세션을 무효화하고 쿠키를 삭제한다.
   - 비밀번호 변경이나 탈퇴에 성공하면 그 사용자의 **모든 세션**(다른 기기 포함)을 무효화한다.
- 세션에 저장된 역할과 사용자 정보는 로그인 시점 값이다. 요청마다 DB에서 다시 읽지 않는다.
- 계정 존재 여부: 가입 API는 이메일 중복(409 `1001`)으로 계정이 있는지 알려 준다. 사용성을 위해 허용한다.
- 계정 잠금과 로그인 시도 횟수 제한은 없다.

### 비밀번호 규칙
- 적용 대상: 가입의 비밀번호, 비밀번호 변경의 새 비밀번호.
- 8자 이상 12자 이하다.
- 영문, 숫자, 특수문자(`!@#$%^&*`) 중 2종류 이상을 쓴다. 영문 대문자와 소문자는 한 종류로 센다. 그 밖의 문자는 쓸 수 없다.
- 확인용 입력(로그인, 비밀번호 변경의 기존 비밀번호, 탈퇴)은 비어 있지 않은지만 본다. 규칙이 생기기 전에 가입한 사용자에게 재설정을 강제하지 않는다.

## 인가 규칙

URL 단계(보안 필터)에서 역할을 확인하고, 서비스 단계에서 자원의 소유자를 확인한다. **두 단계를 모두 통과해야 한다.** URL 규칙만으로는 남의 자원을 막지 못한다.

- **역할(URL 단계)의 원본은 `SecurityConfig`의 역할별 matcher 목록이다.** 목록을 고칠 때의 규칙은 `api/src/main/java/com/ecommerce/api/auth/CLAUDE.md`에 있다.
- 아래 표는 서비스 단계의 소유·조건 검사와, 그 검사가 막는 것이다.

| 행위 | 소유·조건 검사 (서비스) | 명시적으로 막는 것 |
|---|---|---|
| 가입 | `ADMIN` 역할 거절 | 관리자 자가 가입 |
| 상품 목록·상세, 카테고리 목록, 리뷰 목록 | 삭제된 상품 제외 | — |
| 내 정보 수정, 비밀번호 변경, 탈퇴 | 본인만(세션의 사용자 ID로 처리) | 남의 정보 수정 |
| 상품 등록, 상품 수정·이미지 교체·삭제, 재고 수정 | 자기 상품만. 아니면 403. 붙이는 이미지는 본인이 올린 것만. 아니면 404 | 남의 상품, 남의 이미지 |
| 업로드 URL 발급, 업로드 완료 등록 | 이미 다른 사람이 등록한 경로면 거절(400). 아직 등록되지 않은 경로는 경로를 아는 판매자 누구나 등록할 수 있다(경로에 UUID가 있어 추측하기 어려워 허용) | 남의 경로 가로채기 |
| 장바구니 전체 | 자기 항목만. 아니면 404 | — |
| 주문 생성, 내 주문 목록, 주문 상세 | 주문에 쓰는 장바구니 항목과 쿠폰은 자기 것만, 상세는 주문자 본인만. 아니면 404 | 남의 주문 보기, 남의 쿠폰 쓰기 |
| 리뷰 작성·수정 | 작성: 구매확정 이력 필요. 수정: 작성자만, 아니면 404 | 구매하지 않은 상품 리뷰 |
| 주문항목 목록 | `orderId` 방식은 `BUYER`이면서 주문자 본인, `sellerId` 방식은 `SELLER`이면서 `sellerId` = 본인 | 다른 판매자의 판매 내역 |
| 주문항목 상세 | 구매자 본인 또는 해당 상품 판매자만. 아니면 404 | 제3자 조회 |
| 배송 시작·배송 완료 | 해당 상품 판매자만. 아니면 404 | 다른 판매자 |
| 구매확정 | 주문자 본인만. 아니면 404 | — |
| 주문항목 취소 | 주문자 또는 해당 상품 판매자. 아니면 404 | 제3자 취소 |

**404와 403을 쓰는 기준(의도된 규칙)**
- 사용자 소유 자원(주문, 주문항목, 리뷰, 장바구니 항목, 발급 쿠폰, 업로드 이미지)의 소유자가 아니면 **404**와 그 자원의 "없음" 코드로 응답해 자원이 있는지조차 알려주지 않는다. 경로의 ID로 접근하든 요청 본문에서 참조하든 같다.
  - 예외: 업로드 완료 등록에서 남이 이미 등록한 경로는 400 `8002`다. 경로는 클라이언트가 만든 값이지 자원 ID가 아니다.
- 공개 자원(상품, 재고)의 소유자가 아니면 **403**이다.
- 새 기능도 이 기준을 따른다.

## 관리 포트와 부하테스트 우회

- 관리 포트(8090)의 `health`와 `prometheus`는 인증 없이 열려 있다. 이 포트는 인프라 방화벽에서 모니터링 수집기만 접근하게 막는다. 관리 포트를 외부에 여는 것은 금지다.
- **부하테스트용 인증 우회**
  - 동작 방식: `X-LoadTest-User-Id`와 `X-LoadTest-Secret` 헤더로 로그인 없이 해당 사용자로 인증하고, 그 요청의 CSRF 검사를 건너뛴다.
  - 켜지는 조건: `loadtest` 프로필이 활성화되어 있고 `app.loadtest.auth.enabled=true`여야 한다. 켜졌는데 비밀값이 빈 문자열이면 서버가 시작되지 않는다.
  - 우회를 켤 때는 반드시 추측할 수 없는 비밀값을 명시적으로 설정한다. 환경변수를 빠뜨리면 공개된 문자열이 비밀값이 되는 결함이 있다(`docs/tracking/findings/auth-user.md`).
  - 실패 처리: 비밀값이 틀리거나, 사용자 ID 형식이 틀리거나, 탈퇴한 사용자면 401이다. 헤더가 있으면 세션이 있어도 비밀값부터 검사한다.
  - **실제 사용자가 있는 환경에서는 절대 켜지 않는다.** 부하테스트 환경에서만 쓴다.
- CORS는 `http://localhost:3000`에서 쿠키를 포함한 요청만 허용한다.

## 자격 증명 관리

| 자격 증명 | 생성·저장 | 수명·폐기 |
|---|---|---|
| 사용자 비밀번호 | 가입·변경 시 BCrypt 해시로 `users.password`에 저장. 원문은 저장하지 않고 로그도 남기지 않는다 | 변경 시 덮어씀. 탈퇴 후에도 해시는 남음(숨김 삭제) |
| 로그인 세션 | `GET /auth/csrf`에서 Redis `ecommerce:session`에 생기고, 로그인은 같은 세션을 인증 상태로 만든다. 세션에는 principal(`CustomUserDetails`)이 Java 직렬화되어 들어간다. 비밀번호 해시도 함께 들어가는 결함은 `docs/tracking/findings/auth-user.md`에 있다 | 30분 무활동 만료. 로그아웃과 비밀번호 변경·탈퇴 때의 폐기 범위는 위 "세션 종료". Redis를 잃으면 모든 세션이 사라져 전원 재로그인 |
| CSRF 토큰 | 세션에 저장 | 세션과 수명이 같다 |
| DB·Redis 비밀번호, GCP 설정 | 로컬은 커밋되지 않는 `application-secret.yaml`, 클라우드는 인스턴스 환경변수. **로컬에서 만든 jar나 이미지는 외부로 내보내지 않는다.** 비밀 설정 파일이 그 안에 들어간다(`docs/tracking/findings/ops-k6.md`). 배포 이미지는 배포 워크플로에서만 만든다 | 교체하려면 설정을 바꾸고 재시작 |
| GCP 서비스 계정 | Application Default Credentials(환경변수 `GOOGLE_APPLICATION_CREDENTIALS`가 가리키는 키 파일, 또는 VM 서비스 계정) | 키 파일은 저장소에 두지 않는다 |
| 배포 인증 | GitHub Actions → GCP Workload Identity 연동(장기 키 없음) | — |
| 부하테스트 비밀값 | `LOADTEST_AUTH_SECRET` 환경변수 | 부하테스트 환경에만 둔다 |

## 민감 정보 처리

- 비밀번호 원문, 세션 ID, 자격 증명은 응답이나 로그에 남기지 않는다.
- 이메일은 본인 프로필과 관리자 회원 목록에만 나온다.
- 주문 목록에서 판매자에게 보이는 구매자 정보는 ID와 닉네임뿐이다. 판매자·상품 정보는 주문 시점 스냅샷으로 보인다.
- 처리되지 않은 예외는 서버 로그에 스택과 함께 남기고, 클라이언트에는 일반 문구만 보낸다.

## 감사 기록

- 별도의 감사 로그(누가 언제 무엇을 바꿨는지)는 없다.
- 남는 기록
  - 엔티티의 생성·수정 시각. 단, 주문항목은 배송 완료 시각만 남고, 배송 시작·구매확정·취소 시각은 남지 않는다.
  - 쿠폰 사용 스냅샷(사용 시각·할인액)
  - 멱등 키 기록. 만료돼도 지우는 정리 작업이 없어 쌓인다([결정 기록 0001](adr/0001-order-idempotency.md)).
  - 애플리케이션 로그(예외, 낙관적 락 충돌, 캐시·조회수 반영 실패)
