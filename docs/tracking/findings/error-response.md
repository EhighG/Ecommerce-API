# 미해결 문제: 오류 응답·응답 형식

## 쿼리 파라미터 조건 위반이 500으로 응답된다
- **필요성**: 5/10. `size=30` 같은 흔한 입력 실수가 500이 되어 서버 오류 지표를 오염시킨다(재현 확인).
- **재현**: `GET /api/products?size=30`을 호출하면 `500 {"code":"9999"}`가 온다(MockMvc로 확인). 아래도 같은 증상이다.
  - `GET /api/order-items`에 `orderId`와 `sellerId`를 둘 다 주거나 둘 다 빼는 경우, 구매자 조회에 `statusList`를 주는 경우
  - `GET /api/reviews?searchBy=PRODUCT`에서 `productId`를 뺀 경우
- **원인**: `@ModelAttribute`로 바인딩되는 record의 compact constructor에서 `AppException`을 던지면, 바인딩 단계에서 다른 예외로 감싸진다. 그러면 전역 핸들러의 `Exception` 분기로 떨어진다.
- **영향**: 클라이언트 입력 실수가 서버 오류로 집계되어 오류율 지표와 알림을 오염시킨다. 사용자는 원인을 알 수 없다.
- **지금 해결하지 않는 이유**: 코드 변경이 필요해서 오류 응답 정리 작업으로 분리했다.
- **고칠 방향(2026-09-30 결정)**: 필드 사이 조건을 record의 `@AssertTrue` 메서드로 옮긴다. 전용 코드가 필요한 검사(가입의 `1002`)만 서비스에서 한다. 핸들러에서 원인 예외를 풀어 주는 방식은 쓰지 않는다. 프레임워크가 예외를 감싸는 내부 방식에 기대게 되고, 생성자 검사를 금지한 `standards.md` 규칙과도 어긋나기 때문이다.

## 본문 교차 검증 오류가 전용 코드 없이 `"요청 Body 읽기 실패"`로 응답된다
- **필요성**: 3/10. 비밀번호 확인 불일치 같은 검사는 보통 클라이언트가 먼저 막는다. 위 항목과 함께 고친다.
- **재현**: `POST /api/users`에 `password`와 `passwordCheck`를 다르게 보내면 `400 {"code":"9001","message":"요청 Body 읽기 실패"}`가 온다(MockMvc로 확인). `1002`는 클라이언트에 도달하지 않는다. 가입 역할 `ADMIN`, 상품 수정 본문의 두 필드 누락도 같다.
- **원인**: `@RequestBody` record의 생성자에서 던진 `AppException`을 Jackson이 감싸고, Spring은 이것을 `HttpMessageNotReadableException`으로 바꾼다. 전역 핸들러가 이 타입을 먼저 잡는다.
- **영향**: 가입 화면에서 비밀번호 불일치 같은 흔한 오류를 사용자에게 구체적으로 알릴 수 없다.
- **지금 해결하지 않는 이유**: 코드 변경이라 별도 작업으로 한다. 위 항목과 같은 방향으로 함께 고친다.

## 쿼리 파라미터 타입이 틀리면 영문 프레임워크 메시지가 노출된다
- **필요성**: 3/10. 내부 클래스 이름이 드러나는 정도다.
- **재현**: `GET /api/products?sortBy=XX` → `400 {"code":"9001","message":"Failed to convert value of type 'java.lang.String' to required type 'com.ecommerce.api.product.enums.SortType'; …"}`. enum만이 아니라 숫자 파라미터(`page=abc`, `orderId=x`)도 같다. 쿼리는 모두 `@ModelAttribute` record로 받아 `BindException`의 문구가 그대로 나가기 때문이다.
- **영향**: 내부 클래스 이름이 노출되고, 사용자에게 보여줄 수 없는 메시지가 나간다.
- **지금 해결하지 않는 이유**: 오류 응답 정리 작업에서 함께 처리한다.
- **고칠 때**: 잘못된 `sortBy`에는 지금 어디서도 던지지 않는 `2003`(`INVALID_SORT_TYPE`)을 쓴다.

## 입력 길이 제한이 컬럼보다 느슨한 필드가 있다
- **필요성**: 4/10. 30자를 넘는 실제 이메일은 가입이 500이 되고, 아주 긴 쿠폰 기간은 되돌릴 수 없는 이벤트를 만든다.
- **조건**: 아래 필드에 컬럼 길이를 넘는 값을 보낸다.
  - 가입 이메일: 검증은 형식만 보고, 컬럼은 30자
  - 내 정보 수정의 닉네임: 검증은 공백 여부만 보고, 컬럼은 20자. 가입할 때는 20자 검증이 있다
  - 상품 등록의 상품명: 검증은 공백 여부만 보고, 컬럼은 50자
  - 쿠폰 이벤트 생성의 이름: 검증은 공백 여부만 보고, 컬럼은 100자
  - 쿠폰 이벤트 생성의 유효기간과 발급 종료 시각: 하한만 검사한다. 아주 큰 값이면 이벤트는 만들어지지만, 발급할 때 시각 계산이 넘치거나 컬럼 범위를 넘어 아무도 발급받지 못한다. 이벤트를 수정하거나 끄는 기능도 없다.
- **요구사항(쿠폰 이벤트, 2026-09-30 확정)**: 이름은 100자 이하, 유효기간은 최대 365일, 발급 종료 시각은 생성 시점부터 최대 1년 뒤다.
- **증상**: DB 오류가 처리되지 않아 500(`9999`)이 된다.
- **영향**: 사용자는 입력을 어떻게 고쳐야 할지 알 수 없고, 입력 실수가 서버 오류 지표에 잡힌다.
- **지금 해결하지 않는 이유**: 허용 길이를 정해야 한다(검증을 컬럼에 맞출지, 컬럼을 늘릴지). 오류 응답 정리 작업에서 함께 결정한다.

## 전역 핸들러가 5xx `AppException`을 로그로 남기지 않는다
- **필요성**: 3/10. 해당하는 코드가 몇 개뿐이고 운영 환경이 없다.
- **증상**: `AppException` 핸들러는 응답만 만들고 로그를 남기지 않는다. 재고 행 없음(`2500`)과 통계 행 없음(`2006`)은 던지는 곳에서 상품 ID와 함께 `log.error`를 남긴다(조회수 반영 경로는 호출하는 쪽이 남긴다). 취소의 쿠폰 복구 실패(`7511`)도 던지는 곳에서 발급 쿠폰 ID와 함께 남긴다. 하지만 `7504`, `7505`, `7508`, `9000`은 남지 않을 수 있다(`9000`은 지금 던지는 곳이 없다).
- **영향**: 이 오류로 500이 나도 서버 로그에서 원인을 찾기 어렵다.
- **지금 해결하지 않는 이유**: 취소 쿠폰 락 순서 작업(2026-10-08)의 범위 밖이라 기록만 한다. 핸들러에서 한꺼번에 남기면 관련 ID를 알 수 없다. 예외 메시지는 응답으로 나가므로 ID를 넣을 수도 없다. 그래서 던지는 곳마다 남길지 함께 정해야 한다.

## 없는 상품의 재고를 수정하면 500으로 응답한다
- **필요성**: 2/10. 판매자의 입력 실수에서만 생긴다.
- **재현**: 판매자가 `PATCH /api/products/inventory`에 없는 상품 ID를 보낸다(코드로 확인).
- **증상**: 재고 행을 먼저 조회하므로 404 `2000`이 아니라 500 `2500`이 나오고, 재고 행이 없다는 `log.error`가 남는다. 상품은 있는데 재고 행만 없는 경우는 데이터 이상이라 500이 맞다(`inventory/CLAUDE.md`). 상품 자체가 없는 클라이언트 입력 실수까지 같은 500이 되는 것이 문제다.
- **영향**: 클라이언트 입력 실수가 서버 오류 지표와 error 로그에 잡힌다. 데이터가 깨진 경우와 로그만으로는 구분하기 어렵다.
- **지금 해결하지 않는 이유**: 취소 쿠폰 락 순서 작업(2026-10-08)에서 재고 행 없음 로그를 추가하다가 발견했다. 응답 코드 변경이라 오류 응답 정리 작업에서 함께 본다.

## 남의 자원에 주는 404가 오류 코드로 존재를 드러낸다 (방향 미정)
- **필요성**: 2/10. 드러나는 것은 그 ID의 자원이 있다는 사실뿐이다. 문서를 코드에 맞추는 후보로 끝낼 수도 있다.
- **조건**: 로그인한 사용자가 남의 주문, 주문항목, 리뷰의 ID로 조회하거나 변경한다.
- **증상**: HTTP 상태(404)와 메시지는 "없음"과 같지만 `code`가 다르다. 주문은 `3000`(없음)과 `3001`(남의 것), 주문항목은 `3002`와 `3001`, 리뷰는 `6000`과 `6003`이다. 같은 "남의 주문"이라도 주문항목 목록의 구매자 조회(`OrderItemService`)는 `3000`을 준다.
- **영향**: 주문과 주문항목 ID는 순번이라, 대입해 보면 남의 주문이 있는지 알 수 있다. 문서도 서로 다르다. `security.md`와 `business-rules.md`는 "존재 자체를 숨긴다"고 하고, API 명세(`docs/api/openapi.yaml`)와 `standards.md`는 코드를 구분해 공개한다.
- **지금 해결하지 않는 이유**: 요구사항 방향을 사용자가 나중에 정한다(2026-09-30 문서 동기화 작업에서 보류).
- **후보**: (a) 남의 자원에도 "없음" 코드를 던지고 `3001`과 `6003`은 은퇴시킨다. (b) 문서를 "상태와 메시지만 같고 `code`로는 구분된다"로 낮춘다.

## 값이 없는 응답 필드를 빼는 곳과 `null`로 보내는 곳이 섞여 있다 (방향 미정)
- **필요성**: 2/10. 응답 모양을 통일하는 문제다.
- **증상**: `OrderItemListRes`와 `UserReviewListRes`는 값이 없으면 필드를 뺀다(`@JsonInclude(NON_NULL)`). 상품 기준 리뷰 목록, 주문항목 검색 응답, 상품 목록은 `null`로 보낸다. 그래서 같은 리뷰의 `content`가 상품 기준 목록에서는 `null`이고, 작성자 기준 목록과 프로필에서는 필드가 없다. 역할이나 검색 기준에 따라 모양이 달라지는 필드(`reviewSection`, `productReviews`/`userReviews`)는 의도적으로 뺀다.
- **영향**: 클라이언트가 두 경우를 모두 처리해야 한다. 공통 규칙이 없어서 새 DTO도 제각각이 된다.
- **지금 해결하지 않는 이유**: 요구사항 방향을 사용자가 나중에 정한다(2026-09-30 문서 동기화 작업에서 보류).
- **후보**: (a) 값 필드는 항상 넣고 없으면 `null`로 보내며, 모양이 달라지는 필드만 뺀다. (b) 값이 없으면 전부 뺀다(전역 설정). (c) 지금 상태를 DTO별로 문서화한다.
