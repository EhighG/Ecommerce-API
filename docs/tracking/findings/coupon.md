# 미해결 문제: 쿠폰

## 쿠폰 발급 수량 한도를 Redis만 판정해서 초과 발급될 수 있다
- **필요성**: 7/10. Redis가 과거 상태로 복원되거나 발급 도중 끊겨야 해서 드물다. 일어나면 이 프로젝트의 핵심인 쿠폰 수량 한도가 깨진다.
- **조건**: Redis가 과거 시점 데이터로 되살아난다. 비정상 종료 후 오래된 RDB 스냅샷으로 재시작하거나, 비동기 복제 구성에서 장애 조치가 일어나는 경우다. 또는 Redis를 잃은 순간 이미 Redis 단계를 통과했지만 아직 DB에 커밋하지 않은 발급이 있다.
- **증상**
  - 발급 Lua 스크립트는 Redis `stock` 값만 보고 남은 수량을 판정한다(`CouponEventCacheService`). DB 저장 때는 발급 건수를 검사하지 않는다(`CouponService.issue`).
  - 캐시 재적재는 meta 키가 없을 때만 일어난다. 그래서 과거 상태로 복원된 Redis는 meta 키가 남아 있어 다시 적재되지 않고, 실제보다 큰 `stock`으로 그 차이만큼 더 발급된다.
  - 재적재는 DB에서 건수를 센 뒤 초기화하는데, 두 단계가 원자적이지 않다(`CouponEventCacheScheduler`). 그래서 진행 중이던 발급 수만큼 수량이 많게 잡힌다.
  - DB의 (이벤트, 사용자) 유니크 제약은 1인 1장만 막는다.
- **영향**: 이벤트 발급 수가 준비 수량(`initialQuantity`)을 넘는다. 문서(`business-rules.md`)가 유니크 제약을 "최종 방어선"이라고 적어서 수량도 DB가 막는 것처럼 읽혔다(2026-09-30 동기화 작업에서 바로잡음). 코드 경로로 분석했고, Redis 영속화·복제 구성은 저장소에 없어서 추정이다.
- **고칠 방향 후보**
  1. DB에도 상한을 둔다. `coupon_event`에 발급 건수 컬럼을 두고 조건부로 증가시킨다. DDL이 필요하고, 모든 발급이 이벤트 행 하나를 잠가 선착순 부하의 병목이 되므로 k6로 비용을 먼저 잰다.
  2. 운영 규칙으로 막는다. Redis 영속화를 끄고 장애 조치 구성을 쓰지 않는다. 재시작한 Redis는 비어 있어 DB 기준으로 다시 적재된다. 대가로 재시작마다 모든 세션이 사라진다.
  3. 스케줄러가 "DB 발급 수 + Redis 남은 수량"을 초기 수량과 주기적으로 대조해 보정한다.
- **지금 해결하지 않는 이유**: 방식마다 비용이 커서 Redis 장애 대응(대체 동작 포함)과 함께 설계한다. `status.md` 남은 작업 "Redis 장애 대응 보강"에서 다룬다.

## 쿠폰 발급 실패 때 Redis 수량을 되돌리지 못하는 경우가 있다
- **필요성**: 3/10. 커밋 실패나 Redis 실패가 겹쳐야 생기고, 덜 발급되는 방향이라 한도는 지켜진다.
- **증상**: 발급의 DB 저장이 실패하면 `compensateIssue`로 Redis 수량과 발급자 표시를 되돌린다. 하지만 두 경우에는 수량이 1 줄어든 채 남는다.
  - 커밋 단계에서 실패하는 경우: 되돌리기는 메서드 안의 예외에만 걸려 있다.
  - 되돌리는 Redis 호출 자체가 실패하는 경우: 보상 호출에 예외 처리가 없다. 이때는 보상 예외가 원래 오류(`7506`, `1000` 등)를 덮어 500(`9999`)으로 응답된다.
- **영향**: 준비 수량보다 적게 발급될 수 있다. 한도를 넘는 방향은 아니다.
- **지금 해결하지 않는 이유**: `status.md` 남은 작업 "Redis 장애 대응 보강"에서 함께 설계한다.

## 쿠폰 이벤트를 만들 때 Redis 적재가 커밋 전에 일어나고, 실패하면 생성이 실패한다
- **필요성**: 3/10. 관리자만 겪고, 발급 기간이 이미 시작된 이벤트를 만들 때 Redis가 실패해야 한다. 실패가 드러나므로 다시 만들면 된다.
- **조건**: 발급 기간이 이미 시작된 쿠폰 이벤트를 만든다.
- **증상**
  - `CouponService`는 DB 커밋 전에 이벤트를 Redis에 바로 적재한다. Redis가 실패하면 이벤트 생성 전체가 롤백되고 500(`9999`, 직렬화 실패면 `7508`)이 된다.
  - 적재 직후, 커밋 전의 짧은 구간에 발급 요청이 오면 캐시는 있지만 DB에 이벤트가 없다. 그래서 404 `7500`이 난다(보상은 됨).
- **영향**: 스케줄러가 30초 안에 적재해 줄 수 있는데도, Redis 장애가 이벤트 생성까지 막는다.
- **고칠 방향**: 즉시 적재를 커밋 뒤로 옮기고, 실패하면 로그만 남기고 스케줄러에 맡긴다.
- **지금 해결하지 않는 이유**: `status.md` 남은 작업 "Redis 장애 대응 보강"에서 함께 본다.

## 쿠폰 발급이 DB 무결성 오류를 모두 "이미 발급받은 쿠폰"으로 응답한다
- **필요성**: 2/10. 실제로 일어날 경로는 아주 긴 유효기간뿐이고, `error-response.md`의 입력 길이 제한을 고치면 그 경로도 사라진다.
- **증상**: `CouponService.issue`가 `DataIntegrityViolationException` 전체를 `7506`으로 바꾼다. 유니크 위반뿐 아니라 시각 컬럼 범위 초과(아주 긴 유효기간) 같은 오류도 `7506`이 된다(발생 조건은 추정).
- **영향**: 처음 받는 사용자도 "이미 발급받은 쿠폰"이라는 안내를 받고, 운영자는 발급 장애를 중복 요청으로 오인한다.
- **고칠 방향**: 유니크 제약(`uk_coupon_issued_event_user`) 위반일 때만 `7506`으로 바꾸고, 나머지는 서버 오류로 둔다. `error-response.md`의 "입력 길이 제한" 항목의 쿠폰 이벤트 상한이 들어가면 실제로 일어날 경로도 사라진다.
- **지금 해결하지 않는 이유**: 오류 응답 정리 작업에서 함께 처리한다.

## 정액 쿠폰 이벤트도 최대 할인액을 필수로 받는다
- **필요성**: 3/10. 관리자가 불편한 정도다. 할인값보다 작은 최대 할인액을 넣으면 할인액이 조용히 줄어드는 함정은 있다.
- **증상**: 쿠폰 이벤트를 만들 때 할인 방식과 관계없이 최대 할인액(1 이상)이 필수다. 정액 쿠폰은 할인값이 곧 할인액이라 최대 할인액이 의미가 없다.
- **요구사항(2026-09-30 확정)**: 최대 할인액은 정률 쿠폰에만 받는다. 정액 쿠폰에는 필요 없다.
- **영향**: 관리자가 의미 없는 값을 넣어야 한다. 정액 쿠폰에 할인값보다 작은 최대 할인액을 넣으면, 할인액이 조용히 그 값으로 줄어든다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. 바꿀 때 기존 정액 이벤트의 값, `UsedCoupon` 스냅샷과 응답 필드(`maxDiscountAmount`)를 어떻게 둘지 함께 정한다.

## 쿠폰 이벤트를 수정하거나 끌 수 없다
- **필요성**: 4/10. 잘못 만든 이벤트를 되돌릴 수 없다. 다만 발급된 쿠폰과 Redis 캐시를 어떻게 다룰지 규칙부터 정해야 하는 큰 작업이다.
- **증상**: 이벤트를 만든 뒤 바꾸거나 비활성화하는 API가 없다. `active` 필드는 있지만 바꾸는 경로가 없다.
- **요구사항(2026-09-30 확정)**: 관리자가 쿠폰 이벤트를 수정하고 끌 수 있어야 한다.
- **영향**: 관리자가 이벤트를 잘못 만들면(수량, 기간, 할인값) 되돌릴 방법이 없다. 이벤트가 이미 Redis에 올라가 있으면, 수정이나 비활성화를 캐시에도 반영해야 한다(재적재는 meta 키가 없을 때만 일어난다).
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. 이미 발급된 쿠폰과 진행 중인 발급에 어떤 영향을 줄지(예: 수량을 발급 수보다 적게 줄이기) 규칙을 먼저 정해야 한다.
