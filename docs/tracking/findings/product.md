# 미해결 문제: 상품·미디어·리뷰·장바구니

## 기존 장바구니 항목에 동시에 담으면 수량이 유실될 수 있다
- **조건**: 같은 구매자가 이미 담긴 상품을 거의 동시에 두 번 담는다(더블클릭, 재시도).
- **증상**: 두 요청 모두 기존 행을 읽고 각자 수량을 더해 저장한다. 그래서 한 번만 더해진다(lost update). 처음 담는 경우의 동시 요청만 유니크 제약으로 409(`7001`)가 된다.
- **영향**: 장바구니 수량이 사용자 의도보다 적다. 주문 전에 사용자가 확인할 수 있어서 금전 피해는 없다.
- **지금 해결하지 않는 이유**: 수정 방식을 정해야 한다. 조건부 UPDATE(`quantity = quantity + ?`), 낙관적 락, 멱등 키 중 무엇을 쓸지는 장바구니 작업에서 결정한다.

## 이미지 목록에 같은 순서나 같은 이미지가 두 번 오면 원인과 다른 오류가 난다
- **조건**: 상품 등록이나 이미지 교체 요청의 `imageIdList`에 같은 `order`를 두 번 넣거나, 같은 `imageId`를 두 번 넣는다.
- **증상**
  - 같은 `order`: `(product_id, display_order)` 유니크 제약 위반이 처리되지 않아 500(`9999`)이 된다.
  - 같은 `imageId`: `findAllById` 결과가 요청 개수보다 적어 `8003`("이미지를 찾을 수 없습니다")이 된다. 이미지는 실제로 있다.
- **영향**: 판매자는 무엇이 잘못됐는지 알 수 없다. 트랜잭션이 롤백되어 데이터가 어긋나지는 않는다.
- **지금 해결하지 않는 이유**: 오류 응답 정리 작업에서 입력 검증(순서 중복, 이미지 ID 중복 거절)과 함께 처리한다.

## Redis 장애 시 공개 상품 상세 조회가 실패한다
- **조건**: Redis에 연결할 수 없다.
- **증상**: `GET /products/{id}`가 조회수 증가(`INCR`)에서 예외를 받아 500(`9999`)이 된다.
- **영향**: 조회수 손실은 허용하기로 했는데, 조회수 때문에 가장 많이 쓰이는 공개 API가 함께 멈춘다. 단, 세션과 쿠폰 발급도 Redis에 의존하므로 Redis 장애의 전체 영향은 이보다 크다.
- **지금 해결하지 않는 이유**: 조회수 증가 실패를 삼킬지(로그만 남김), 비동기로 돌릴지 정하는 별도 작업이다. `status.md` 남은 작업 "Redis 장애 대응 보강"에서 함께 본다.

## 삭제된 상품에 대한 요청의 응답 코드가 경로마다 다르다
- **증상**: 상품 수정, 이미지 교체, 상품 삭제, 리뷰 작성은 삭제된 상품이면 404 `2000`(없음)이다. 재고 수정과 리뷰 수정은 400 `2004`(삭제된 상품)다. 주문은 상품을 지울 때 장바구니 항목도 지워지므로 대개 404 `7000`이고, `2004`는 삭제와 주문이 겹치는 순간에만 나온다. 재고 수정은 삭제 여부를 소유자보다 먼저 봐서, 남의 삭제된 상품에도 403 대신 400이 나온다.
- **영향**: 클라이언트가 같은 상황(삭제된 상품)을 엔드포인트마다 다른 코드로 처리해야 한다.
- **고칠 방향 후보**: (a) "삭제된 상품은 없는 상품이다"로 정하고 404 `2000`으로 통일한다. 상품 상세와 목록이 삭제된 상품을 404로 숨기는 것과 같은 기준이고, `2004`는 은퇴시킨다(2026-09-30 동기화 작업의 추천). (b) 400 `2004`로 통일한다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다(2026-09-30 동기화 작업에서 보류). 방향도 그때 확정한다.

## 같은 리뷰를 동시에 수정하면 상품 평점 합계가 틀어진다
- **조건**: 같은 리뷰에 수정 요청 두 개가 겹친다(더블클릭, 두 기기).
- **증상**: `ReviewService`는 리뷰를 락 없이 읽어 이전 별점을 얻고, "새 값 − 이전 값"을 `product_stat.rating_sum`에 더한다. `Review`에는 `@Version`이 없다. 두 요청이 같은 이전 값을 기준으로 계산해 변화량이 둘 다 더해지지만, 리뷰에는 한쪽 값만 남는다(예: 4→6과 4→8이 겹치면 합계 +6).
- **영향**: 상품 평점과 평점 정렬이 실제 리뷰 별점과 영구히 어긋난다.
- **고칠 방향**: 수정할 때 리뷰 행을 `FOR UPDATE`로 먼저 잠근다(DDL 불필요). 이 경로는 리뷰 → `product_stat` 순서로 락을 잡으며, 주문 경로(`inventory` → `product_stat`)와 겹치는 테이블은 `product_stat`뿐이다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. 다른 락 작업과 함께 본다.

## 업로드 이미지 경로(`object_key`)에 유니크 제약이 없다
- **조건**: 같은 경로에 대한 업로드 완료 등록 요청 두 개가 동시에 들어온다(재시도, 더블클릭, 또는 서로 다른 판매자).
- **증상**: `MediaService`는 경로로 조회한 뒤 없으면 저장한다. `uploaded_image.object_key`에는 유니크 제약이 없어서, 두 요청이 모두 조회를 통과하면 같은 경로로 행이 두 개 생긴다. 이후 그 경로의 등록 요청은 조회 결과가 두 건이라 영구히 500이 된다. 서로 다른 판매자가 동시에 등록하면 둘 다 성공해 "남이 등록한 경로면 거절" 규칙이 깨진다.
- **고칠 방향**: `object_key`에 유니크 제약을 추가한다(DDL을 모든 DB에 직접 적용, 절대 규칙 4). 위반이 나면 기존 행을 다시 조회해 멱등 규칙대로 응답한다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. DDL 적용 작업과 함께 한다.

## 작성자 기준 리뷰 목록과 프로필에 삭제된 상품의 리뷰가 나온다
- **증상**: `GET /reviews?searchBy=WRITER`와 구매자 프로필의 최근 리뷰 5개가 상품 삭제 여부로 거르지 않는다. 삭제 여부를 알려 주는 필드도 없다(썸네일만 `null`이 된다).
- **요구사항(2026-09-30 확정)**: 작성자 기준 리뷰 목록과 프로필(최근 5개, 전체 개수)에서도 삭제된 상품의 리뷰를 뺀다. 상품 기준 목록은 지금처럼 404다. `security.md`의 "리뷰 목록은 삭제된 상품 제외"와 같은 기준이다.
- **영향**: 클라이언트가 삭제된 상품으로 링크하면 404를 만난다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다.

## 리뷰를 상품당 한 사람 1개만 쓸 수 있다(요구사항과 다름)
- **증상**: `Review`에 `(writer_id, product_id)` 유니크 제약(`uk_review_writer_product`)이 있다. 작성 자격은 "그 상품에 구매확정된 주문항목이 하나라도 있는가"로 판정한다(`ReviewService`). 그래서 같은 상품을 여러 번 사도 리뷰는 하나뿐이다.
- **요구사항(2026-09-30 확정)**: 리뷰는 **구매확정된 주문항목 1건마다 1개**다. 수량과 관계없이 주문항목 단위로 세고, 같은 상품을 여러 번 사면 여러 개 쓸 수 있다.
- **고칠 때 함께 정할 것**
  - 리뷰가 어느 주문항목에 대한 것인지 연결해야 한다(예: `order_item_id` 컬럼과 유니크 제약). 기존 유니크 제약을 바꾸는 DDL을 모든 DB에 적용해야 한다(절대 규칙 4).
  - 작성 요청이 상품 ID 대신 주문항목 ID를 받을지 정한다.
  - 기존 리뷰를 어느 주문항목에 연결할지 정한다.
  - 평점 통계(합계, 개수)의 계산 방식은 그대로 쓸 수 있다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다.

## 검색어에 한 글자 단어가 섞이면 결과가 0건이 될 수 있다
- **증상**: 상품 검색은 모든 단어에 `+`(필수)를 붙여 FULLTEXT BOOLEAN MODE로 찾는다. 인덱스가 두 글자 단위(`ngram_token_size=2`)라 한 글자 단어는 일치할 토큰이 없어, 결과 전체가 0건이 될 것으로 보인다(예: "파란 티"). MySQL에서 실행해 확인하지는 않았다.
- **고칠 방향**: 두 글자 미만인 단어는 검색어에서 뺀다. 먼저 실제로 0건이 되는지 확인한다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. 참고로 공백만 입력하면 키워드가 없는 것으로 보고 전체 목록을 주며, 이것은 요구사항으로 확정했다.

## 업로드 파일 크기 제한이 없다
- **증상**: 서명 URL은 `Content-Type`만 고정하고 크기 조건이 없다(`GcsClient`). 완료 등록도 `fileSize`를 저장만 하고 검사하지 않는다.
- **요구사항(2026-09-30 확정)**: 업로드 파일은 10MB 이하다.
- **영향**: 판매자가 아주 큰 파일을 공개 버킷에 올려 상품 이미지로 쓸 수 있다. 저장과 전송 비용이 늘 수 있다.
- **고칠 방향**: 서명 URL에 크기 범위 조건(`x-goog-content-length-range`)을 넣고, 완료 등록에서도 크기를 확인한다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다.
