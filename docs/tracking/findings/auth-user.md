# 미해결 문제: 인증·사용자

## 로그인할 때 세션 ID가 바뀌지 않는다 (코드 분석 기준, 실제 확인 필요)
- **근거**: 직접 만든 로그인 필터(`JsonUsernamePasswordAuthenticationFilter`)를 `addFilterAt`으로 등록했다. 이 경우 Spring Security가 폼 로그인에 기본으로 붙이는 세션 전략(세션 고정 보호, CSRF 토큰 교체)이 적용되지 않는다. 필터 기본값이 `NullAuthenticatedSessionStrategy`이기 때문이다.
- **예상 증상**: 로그인 전 `GET /auth/csrf`에서 받은 세션 쿠키(`SESSION`) 값이 로그인 후에도 그대로다.
- **영향**: 세션 고정 공격에 노출된다. 공격자가 심어 둔 세션 ID로 피해자가 로그인하면 공격자도 그 세션을 쓸 수 있다.
- **지금 해결하지 않는 이유**: 실제 동작(Spring Session과의 조합 포함)을 확인해야 하고, 보안 설정 변경이라 사용자 판단이 필요하다.
- **접근 방법**: 필터에 `ChangeSessionIdAuthenticationStrategy`와 `CsrfAuthenticationStrategy`를 조합한 세션 전략을 설정한다. 그다음 로그인 전후로 쿠키 값을 비교하는 테스트를 추가한다.

## 비밀번호 변경·탈퇴 후에도 다른 기기의 세션이 살아 있다
- **조건**: 같은 계정으로 두 곳에서 로그인한 뒤, 한쪽에서 비밀번호를 바꾸거나 탈퇴한다.
- **증상**: 요청한 세션만 무효화된다. 다른 세션은 30분 동안 요청이 없을 때까지 계속 유효하다. 세션에 저장된 사용자 정보는 요청마다 DB에서 다시 확인하지 않는다.
  - 탈퇴한 경우: `…AndDeletedFalse` 조회를 쓰는 API는 404가 되지만, 주문항목 목록처럼 사용자 행을 다시 읽지 않는 API는 계속 동작한다.
- **영향**: 계정 탈취를 알아채고 비밀번호를 바꿔도, 공격자의 세션은 바로 끊기지 않는다.
- **요구사항(2026-09-30 확정)**: 비밀번호 변경이나 탈퇴에 성공하면 그 사용자의 **모든 세션**을 무효화한다. 다른 기기의 세션도 포함한다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다. 구현하려면 사용자별로 세션을 찾는 방법을 정해야 한다(예: Spring Session의 사용자별 인덱스 조회).

## 부하테스트 비밀값을 설정하지 않으면 공개된 문자열이 비밀값이 된다
- **조건**: `loadtest` 프로필에서 `LOADTEST_AUTH_ENABLED=true`로 켜고, `LOADTEST_AUTH_SECRET`은 설정하지 않는다.
- **증상**: 비밀값이 문자 그대로의 `${LOADTEST_AUTH_SECRET}`가 된다. 빈 값 검사(`isBlank`)를 통과해 서버가 정상 기동한다. 코드 분석 기준이며 실행으로는 확인하지 않았다.
- **영향**: 이 문자열을 헤더에 넣으면 누구나 임의의 사용자로 인증된다. 부하테스트 서버가 외부에 열려 있으면 그 데이터 전체가 노출된다.
- **지금 해결하지 않는 이유**: 코드 변경이다. `@NotBlank` 검증에 더해 `${`로 시작하는 값을 거절하도록 바꾸는 것이 제안이며, 보안 설정이라 사용자 판단이 필요하다.

## 세션마다 BCrypt 비밀번호 해시가 Redis에 저장된다
- **조건**: 로그인한다.
- **증상**: 세션 principal(`CustomUserDetails`)이 `passwordHash`를 갖고 있고 `CredentialsContainer`를 구현하지 않는다. 그래서 인증 후에도 해시가 지워지지 않고 Redis 세션에 Java 직렬화로 저장된다.
- **영향**: Redis가 유출되면 활성 사용자의 비밀번호 해시도 함께 유출된다. BCrypt라 바로 원문이 드러나지는 않지만, 오프라인 대입 공격의 재료가 된다.
- **지금 해결하지 않는 이유**: 세션에 저장되는 클래스를 바꾸면 기존 세션 전체가 무효화된다. 배포 시점과 함께 결정해야 한다.

## 판매자 탈퇴 검사와 상품 일괄 삭제 사이에 들어온 주문은 막지 못한다
- **조건**: 판매자가 탈퇴하는 동안 구매자가 그 판매자의 상품을 주문한다. 또는 같은 판매자가 다른 세션에서 상품을 등록한다.
- **증상**: 탈퇴는 진행 중인 주문항목을 잠금 없는 조회(`existsByProductSellerIdAndStatuses`)로 검사한 뒤 상품을 일괄 숨김 삭제한다. 주문 생성은 트랜잭션 시작 시점에 읽은 상품의 삭제 여부만 본다. 그래서 검사 뒤, 삭제 커밋 전에 커밋된 주문은 탈퇴한 판매자의 삭제된 상품에 `주문완료` 항목으로 남는다. 동시에 등록된 상품은 삭제 대상 조회에서 빠져 살아남을 수 있다. 코드 흐름으로 본 경쟁 구간이고, 동시 실행으로 확인하지는 않았다.
- **영향**: 판매자는 로그인할 수 없어 배송을 시작할 수 없다. 구매자가 직접 취소하기 전까지 주문항목이 `주문완료`로 남는다. "진행 중인 주문이 있는 판매자는 탈퇴할 수 없다"는 규칙이 깨진다.
- **지금 해결하지 않는 이유**: 막으려면 주문 생성이 상품 삭제 여부를 락 아래에서 다시 확인해야 한다. 절대 규칙 1의 락 순서와 함께 설계해야 해서 사용자가 나중에 진행한다(2026-09-30 동기화 작업).

## 다른 사용자의 프로필을 조회하면 그 사람의 이메일이 보인다
- **조건**: 로그인한 사용자가 `GET /users/{userId}`로 다른 사람의 프로필을 조회한다.
- **증상**: 응답(`UserProfileRes`)에 조회 대상의 이메일이 들어 있다. 본인 프로필(`/users/me`)과 같은 응답 형식을 쓰기 때문이다.
- **영향**: 로그인만 하면 누구나 ID를 바꿔 가며 다른 사용자의 이메일을 모을 수 있다.
- **요구사항(2026-09-30 확정)**: 다른 사용자의 프로필에는 이메일을 보여 주지 않는다. 이메일은 본인 프로필과 관리자 회원 목록에만 나온다.
- **지금 해결하지 않는 이유**: 사용자가 나중에 진행한다.
