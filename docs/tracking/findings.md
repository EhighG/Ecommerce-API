# 미해결 문제

## 쿼리 파라미터 조건 위반이 500으로 응답된다
- **재현**: `GET /api/products?size=30`을 호출하면 `500 {"code":"9999"}`가 온다(MockMvc로 확인). 아래도 같은 증상이다.
  - `GET /api/order-items`에 `orderId`와 `sellerId`를 둘 다 주거나 둘 다 빼는 경우, 구매자 조회에 `statusList`를 주는 경우
  - `GET /api/reviews?searchBy=PRODUCT`에서 `productId`를 뺀 경우
- **원인**: `@ModelAttribute`로 바인딩되는 record의 compact constructor에서 `AppException`을 던지면, 바인딩 단계에서 다른 예외로 감싸진다. 그러면 전역 핸들러의 `Exception` 분기로 떨어진다.
- **영향**: 클라이언트 입력 실수가 서버 오류로 집계되어 오류율 지표와 알림을 오염시킨다. 사용자는 원인을 알 수 없다.
- **지금 해결하지 않는 이유**: 코드 변경이 필요해서 별도 작업으로 분리했다. 아래 항목과 함께 전역 예외 처리 방식을 정해야 한다.
- **접근 방법**: 조건 검사를 서비스나 `@AssertTrue` 같은 검증으로 옮긴다. 또는 핸들러에서 원인 예외를 풀어 `AppException`이면 그 코드로 응답한다.

## 본문 교차 검증 오류가 전용 코드 없이 `"요청 Body 읽기 실패"`로 응답된다
- **재현**: `POST /api/users`에 `password`와 `passwordCheck`를 다르게 보내면 `400 {"code":"9001","message":"요청 Body 읽기 실패"}`가 온다(MockMvc로 확인). `1002`는 클라이언트에 도달하지 않는다. 가입 역할 `ADMIN`, 상품 수정 본문의 두 필드 누락도 같다.
- **원인**: `@RequestBody` record의 생성자에서 던진 `AppException`을 Jackson이 감싸고, Spring은 이것을 `HttpMessageNotReadableException`으로 바꾼다. 전역 핸들러가 이 타입을 먼저 잡는다.
- **영향**: 가입 화면에서 비밀번호 불일치 같은 흔한 오류를 사용자에게 구체적으로 알릴 수 없다.
- **지금 해결하지 않는 이유**: 코드 변경이라 별도 작업으로 한다. 위 항목과 같은 방식으로 함께 고치는 것이 맞다.

## 쿼리 enum 값이 틀리면 영문 프레임워크 메시지가 노출된다
- **재현**: `GET /api/products?sortBy=XX` → `400 {"code":"9001","message":"Failed to convert value of type 'java.lang.String' to required type 'com.ecommerce.api.product.enums.SortType'; …"}`
- **영향**: 내부 클래스 이름이 노출되고, 사용자에게 보여줄 수 없는 메시지가 나간다.
- **지금 해결하지 않는 이유**: 오류 응답 정리 작업에서 함께 처리한다.

## 기존 장바구니 항목에 동시에 담으면 수량이 유실될 수 있다
- **조건**: 같은 구매자가 이미 담긴 상품을 거의 동시에 두 번 담는다(더블클릭, 재시도).
- **증상**: 두 요청 모두 기존 행을 읽고 각자 수량을 더해 저장한다. 그래서 한 번만 더해진다(lost update). 처음 담는 경우의 동시 요청만 유니크 제약으로 409(`7001`)가 된다.
- **영향**: 장바구니 수량이 사용자 의도보다 적다. 주문 전에 사용자가 확인할 수 있어서 금전 피해는 없다.
- **지금 해결하지 않는 이유**: 수정 방식을 정해야 한다. 조건부 UPDATE(`quantity = quantity + ?`), 낙관적 락, 멱등 키 중 무엇을 쓸지는 장바구니 작업에서 결정한다.

## 로그인할 때 세션 ID가 바뀌지 않는다 (코드 분석 기준, 실제 확인 필요)
- **근거**: 직접 만든 로그인 필터(`JsonUsernamePasswordAuthenticationFilter`)를 `addFilterAt`으로 등록했다. 이 경우 Spring Security가 폼 로그인에 기본으로 붙이는 세션 전략(세션 고정 보호, CSRF 토큰 교체)이 적용되지 않는다. 필터 기본값이 `NullAuthenticatedSessionStrategy`이기 때문이다.
- **예상 증상**: 로그인 전 `GET /auth/csrf`에서 받은 세션 쿠키(`SESSION`) 값이 로그인 후에도 그대로다.
- **영향**: 세션 고정 공격에 노출된다. 공격자가 심어 둔 세션 ID로 피해자가 로그인하면 공격자도 그 세션을 쓸 수 있다.
- **지금 해결하지 않는 이유**: 실제 동작(Spring Session과의 조합 포함)을 확인해야 하고, 보안 설정 변경이라 사용자 판단이 필요하다.
- **접근 방법**: 필터에 `ChangeSessionIdAuthenticationStrategy`와 `CsrfAuthenticationStrategy`를 조합한 세션 전략을 설정한다. 그다음 로그인 전후로 쿠키 값을 비교하는 테스트를 추가한다.

## 비밀번호 변경·탈퇴 후에도 다른 기기의 세션이 살아 있다
- **조건**: 같은 계정으로 두 곳에서 로그인한 뒤, 한쪽에서 비밀번호를 바꾸거나 탈퇴한다.
- **증상**: 요청한 세션만 무효화된다. 다른 세션은 30분 동안 요청이 없을 때까지 계속 유효하다. 세션에 저장된 사용자 정보는 요청마다 DB에서 다시 확인하지 않는다.
  - 탈퇴한 경우: `…AndDeletedFalse` 조회를 쓰는 API는 404가 되지만, 주문항목 목록처럼 사용자 행을 다시 읽지 않는 API는 계속 동작한다.
- **영향**: 계정 탈취를 알아채고 비밀번호를 바꿔도, 공격자의 세션은 바로 끊기지 않는다.
- **지금 해결하지 않는 이유**: 정책 결정이 필요하다(전체 세션 폐기 여부). Spring Session의 사용자별 인덱스 조회를 도입할지도 정해야 한다.

## k6 공용 라이브러리가 문자열 오류 코드를 인식하지 못한다
- **재현**: 오류 응답을 기대하는 k6 체크(`checkApiError`)가 항상 실패하고, 실패 로그에 `code`와 `message`가 빠진다.
- **원인**: 응답 `code`는 문자열인데, `k6/lib/auth.js`의 `readApiError`는 숫자일 때만 오류 본문으로 인정한다. 오류 코드 타입을 문자열로 바꾼 커밋(`337d4f2`) 이후 생겼다.
- **영향**: 부하테스트에서 실패 원인을 분류할 수 없다.
- **지금 해결하지 않는 이유**: `k6/` 아래 여러 스크립트가 아직 커밋되지 않은 상태다. 사용자가 정리하는 범위와 함께 고쳐야 한다.

## k6 주문 시나리오가 `Idempotency-Key`를 보내지 않는다
- **조건**: 저장소의 k6 주문 시나리오(`260519_order_bypass_auth/order-coupon-mixed.js` 등)를 지금 서버에 대고 실행한다.
- **증상**: `k6/` 아래 어떤 스크립트에도 `Idempotency-Key` 헤더가 없다. 주문 생성이 모두 400(`9100`)으로 실패할 것으로 예상된다(코드 검색 기준, 실행으로는 확인하지 않음).
- **영향**: 부하테스트 결과를 재현할 수 없다. `infra/scripts`의 자동 실행 스크립트도 같은 k6 스크립트를 쓴다.
- **지금 해결하지 않는 이유**: `k6/` 아래 여러 스크립트가 아직 커밋되지 않은 상태다. 사용자가 정리하는 범위와 함께 고쳐야 한다.

## 저장소만으로는 DB 스키마를 재현할 수 없다
- **조건**: 새 환경에서 저장소만 가지고 DB를 준비한다.
- **증상**: 전체 DDL 스크립트나 마이그레이션 도구가 없다. `validate` 설정 때문에 스키마 없이는 기동하지 않는다. FULLTEXT 인덱스와 MySQL ngram 옵션은 코드 어디에도 없다.
- **영향**: 새 환경을 준비하거나 클라우드를 다시 올릴 때 로컬 덤프에 의존해야 한다. 스키마 변경이 환경마다 어긋날 수 있다.
- **지금 해결하지 않는 이유**: 현재 방식(변경마다 SQL을 직접 실행)이 운영자의 결정이다. 스크립트를 저장소에 둘지, 도구를 도입할지는 별도로 결정해야 한다.

## 입력 길이 제한이 컬럼보다 느슨한 필드가 있다
- **조건**: 아래 필드에 컬럼 길이를 넘는 값을 보낸다.
  - 가입 이메일: 검증은 형식만 보고, 컬럼은 30자
  - 내 정보 수정의 닉네임: 검증은 공백 여부만 보고, 컬럼은 20자. 가입할 때는 20자 검증이 있다
  - 상품 등록의 상품명: 검증은 공백 여부만 보고, 컬럼은 50자
- **증상**: DB 오류가 처리되지 않아 500(`9999`)이 된다.
- **영향**: 사용자는 입력을 어떻게 고쳐야 할지 알 수 없고, 입력 실수가 서버 오류 지표에 잡힌다.
- **지금 해결하지 않는 이유**: 허용 길이를 정해야 한다(검증을 컬럼에 맞출지, 컬럼을 늘릴지). 오류 응답 정리 작업에서 함께 결정한다.

## 이미지 표시 순서가 중복되면 500이 난다
- **조건**: 상품 등록이나 이미지 교체 요청의 `imageIdList`에 같은 `order`를 두 번 넣는다.
- **증상**: `(product_id, display_order)` 유니크 제약 위반이 처리되지 않아 500(`9999`)이 된다.
- **영향**: 판매자는 무엇이 잘못됐는지 알 수 없다. 트랜잭션이 롤백되어 데이터가 어긋나지는 않는다.
- **지금 해결하지 않는 이유**: 오류 응답 정리 작업에서 입력 검증(순서 중복 거절)과 함께 처리한다.

## 부하테스트 비밀값을 설정하지 않으면 공개된 문자열이 비밀값이 된다
- **조건**: `loadtest` 프로필에서 `LOADTEST_AUTH_ENABLED=true`로 켜고, `LOADTEST_AUTH_SECRET`은 설정하지 않는다.
- **증상**: 비밀값이 문자 그대로의 `${LOADTEST_AUTH_SECRET}`가 된다. 빈 값 검사(`isBlank`)를 통과해 서버가 정상 기동한다. 코드 분석 기준이며 실행으로는 확인하지 않았다.
- **영향**: 이 문자열을 헤더에 넣으면 누구나 임의의 사용자로 인증된다. 부하테스트 서버가 외부에 열려 있으면 그 데이터 전체가 노출된다.
- **지금 해결하지 않는 이유**: 코드 변경이다. `@NotBlank` 검증에 더해 `${`로 시작하는 값을 거절하도록 바꾸는 것이 제안이며, 보안 설정이라 사용자 판단이 필요하다.

## 로컬 빌드 산출물에 비밀 설정 파일이 포함된다
- **조건**: 로컬에서 `./gradlew bootJar`나 `docker build`를 실행한다.
- **증상**: `src/main/resources/application-secret.yaml`(DB·Redis 비밀번호, GCP 설정)이 jar와 이미지 안에 들어간다. `api/.dockerignore`가 없다.
- **영향**: 로컬 이미지를 레지스트리에 올리거나 jar를 공유하면 자격 증명이 유출된다.
- **지금 해결하지 않는 이유**: 비밀 파일 위치를 옮길지(리소스 밖 외부 경로로 import), `.dockerignore`와 `bootJar` 제외 설정을 둘지 결정해야 한다.

## 세션마다 BCrypt 비밀번호 해시가 Redis에 저장된다
- **조건**: 로그인한다.
- **증상**: 세션 principal(`CustomUserDetails`)이 `passwordHash`를 갖고 있고 `CredentialsContainer`를 구현하지 않는다. 그래서 인증 후에도 해시가 지워지지 않고 Redis 세션에 Java 직렬화로 저장된다.
- **영향**: Redis가 유출되면 활성 사용자의 비밀번호 해시도 함께 유출된다. BCrypt라 바로 원문이 드러나지는 않지만, 오프라인 대입 공격의 재료가 된다.
- **지금 해결하지 않는 이유**: 세션에 저장되는 클래스를 바꾸면 기존 세션 전체가 무효화된다. 배포 시점과 함께 결정해야 한다.

## Redis 장애 시 공개 상품 상세 조회가 실패한다
- **조건**: Redis에 연결할 수 없다.
- **증상**: `GET /products/{id}`가 조회수 증가(`INCR`)에서 예외를 받아 500(`9999`)이 된다.
- **영향**: 조회수 손실은 허용하기로 했는데, 조회수 때문에 가장 많이 쓰이는 공개 API가 함께 멈춘다. 단, 세션과 쿠폰 발급도 Redis에 의존하므로 Redis 장애의 전체 영향은 이보다 크다.
- **지금 해결하지 않는 이유**: 조회수 증가 실패를 삼킬지(로그만 남김), 비동기로 돌릴지 정하는 별도 작업이다.
