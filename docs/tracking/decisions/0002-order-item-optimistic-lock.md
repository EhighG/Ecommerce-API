# 0002. 주문항목 상태 동시 변경은 낙관적 락으로 막고 409로 재시도를 유도한다

## 배경
주문항목의 상태 전이(배송 시작, 배송 완료, 구매확정, 취소)에 동시성 보호가 없었다. 예를 들어 취소와 배송 시작이 겹치면 이런 일이 생길 수 있었다.
- 상태는 배송중인데 취소 복구 작업은 실행된다.
- 취소 복구가 두 번 실행된다.

## 결정
- `OrderItem`에 `@Version` 컬럼을 두고 낙관적 락을 쓴다.
- 충돌하면 전역 핸들러가 `OptimisticLockingFailureException`을 409(`3004`, "새로고침 후 다시 시도")로 바꾼다.

## 검토한 대안
- **비관적 락(`SELECT … FOR UPDATE`)**: 같은 주문항목을 동시에 바꿀 일은 매우 드물다. 그런데 모든 상태 변경 요청에 락 비용이 든다. 대신 드물게 생기는 충돌에 409를 주는 쪽을 택했다.

## 결과
- 동시 요청 중 하나만 성공하고, 나머지는 409를 받는다. 클라이언트는 409(`3004`)를 받으면 새로고침한 뒤 재시도하도록 안내해야 한다.
- 상태 변경은 반드시 엔티티를 거쳐야 한다. `@Version`을 우회하는 bulk UPDATE로 상태를 바꾸면 보호가 사라진다.
- 전역 핸들러가 모든 `OptimisticLockingFailureException`을 주문 상태 충돌 메시지로 바꾼다. 다른 엔티티에 `@Version`을 추가하면 응답 코드와 메시지를 따로 나눠야 한다.
