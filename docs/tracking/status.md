## 남은 작업 (우선순위 순)

항목마다 필요성 점수(1~10, 2026-10-09 평가)를 적었다. 10에 가까울수록 해결할 가치가 크다. 발생 조건·확률·영향과, 이 프로젝트의 핵심인 주문·재고·쿠폰 정합성과 얼마나 관련되는지로 매겼고, 고치는 비용은 넣지 않았다. 점수는 항목이 자세히 적힌 곳 한 곳에만 둔다. `findings/`에 있는 항목은 그 파일에, 이 문서에만 있는 항목은 이 문서에 둔다.

1. **Redis 장애 대응 보강**: Redis가 죽거나 과거 상태로 복원될 때의 정합성과 대체 동작(fallback)을 함께 설계한다. `findings/coupon.md`와 `findings/product.md`의 아래 항목을 묶어서 본다.
   - 쿠폰 발급 수량 한도를 Redis만 판정해서 초과 발급될 수 있다
   - 쿠폰 발급 실패 때 Redis 수량을 되돌리지 못하는 경우가 있다
   - 쿠폰 이벤트를 만들 때 Redis 적재가 커밋 전에 일어나고, 실패하면 생성이 실패한다
   - Redis 장애 시 공개 상품 상세 조회가 실패한다
2. **오류 응답 결함 수정**: `findings/error-response.md`의 항목(방향 미정 두 개 제외)과 아래를 함께 본다.
   - 로그인한 사용자의 없는 경로·허용하지 않는 메서드·잘못된 `Content-Type`이 404·405·415가 아니라 500이 되는 문제(전역 핸들러가 모든 예외를 잡음). 필요성 4: 클라이언트 실수가 서버 오류 지표에 섞인다
   - 먼저 조회하고 저장하는 경로가 동시 요청에서 유니크 제약 위반으로 500이 되는 문제: 가입(이메일), 카테고리 생성(이름), 이미지 부착(업로드 이미지), 리뷰 작성(작성자·상품). 장바구니와 쿠폰 발급만 전용 코드로 바꾼다. 필요성 2: 유니크 제약이 데이터를 지키고, 409 대신 500이 나갈 뿐이다
   - 보안 필터 단계(세션 저장소 장애 등)의 500이 `{code, message}`가 아니라 `code` 없는 Spring Boot 기본 오류 JSON으로 나가는 문제. 필요성 2: 세션 저장소가 장애일 때만 생긴다
3. **빠진 기능**: 규칙은 `business-rules.md`의 해당 절에 있다.
   - 상품 상세에서 바로 주문. 필요성 3: 장바구니를 거쳐 같은 일을 할 수 있다
   - 자동 구매확정. 여러 인스턴스에서 동시에 돌아도 안전해야 한다(구현 주의점은 order 모듈 문서). 필요성 5: 구매자가 확정하지 않으면 항목이 `배송완료`로 남는데, 리뷰는 구매확정이 있어야 쓸 수 있다
   - 상품이 걸린 카테고리 삭제 거절(400 또는 409, 전용 오류 코드). 필요성 3: FK가 있어 데이터는 지켜지고, 관리자가 받는 오류만 불친절하다
   - 할인액 0원 쿠폰 적용 거절(쿠폰 전용 오류 코드와 사유 메시지). 필요성 3: 0원 상품이나 아주 작은 금액의 항목에만 생기고, 취소하면 쿠폰을 돌려받는다
   - 쿠폰 이벤트 목록 조회, 내 쿠폰 목록 조회. 필요성 5: 클라이언트가 이벤트나 자기 쿠폰을 찾을 API가 없다
   - 쿠폰 이벤트 수정·비활성화(관리자). 필요성은 `findings/coupon.md`에 있다
4. **테스트가 없는 영역에 테스트 추가**
   - 인증·인가 매트릭스. 필요성 5: 소유자 검사(절대 규칙 3)가 깨지면 잡는다
   - 쿠폰 발급. 필요성 5: 핵심 동시성 기능인데 k6로만 검증했다
   - 상품·검색. 필요성 4: 한 글자 검색어 같은 결함을 잡는다
   - 리뷰 작성·수정, 사용자 탈퇴. 필요성 3: 로직이 단순한 편이다
   - 장바구니의 남은 경계 사례: 삭제된 상품 담기. 필요성 2: 경계 사례 하나다
5. **그 밖의 미해결 문제**: 요구사항과 다른 현재 동작과 결함 가운데 위에 없는 것은 `findings/`의 영역별 파일에 있다. 우선순위는 항목마다 적은 필요성 점수로 본다.
