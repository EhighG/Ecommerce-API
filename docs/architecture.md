# 시스템 구성

프론트엔드 없이 REST API까지만 제공하는 단일 Spring Boot 애플리케이션(`api/`)이다. 같은 애플리케이션을 여러 대 띄워 로드밸런서 뒤에 두는 수평 확장 구조이고, 인스턴스끼리는 서로 통신하지 않는다. 인스턴스 사이에서 공유해야 하는 상태는 전부 MySQL과 Redis에 둔다.

## 구성 요소와 연결

```
클라이언트 ──HTTPS──▶ 로드밸런서 ──HTTP :8081 /api──▶ API 인스턴스 N대 (동일 이미지)
                                                      │
                          ┌───────────────────────────┼──────────────────────────┐
                          ▼                           ▼                          ▼
                  MySQL 8 (JDBC, HikariCP)     Redis (Lettuce)            GCS (Google API)
                  - 모든 도메인 데이터          - 로그인 세션               - 상품 이미지 원본
                  - 멱등성 record               - 쿠폰 이벤트 캐시/재고     - 서명 URL 발급
                                                - 조회수 증가분 버퍼

API 인스턴스 ──HTTP :8090──▶ Prometheus(수집) ──▶ Grafana
클라이언트 ──PUT(서명 URL)──▶ GCS   (이미지 바이트는 API를 거치지 않음)
```

| 구성 요소 | 역할 | 의존 방향 / 경계 |
|---|---|---|
| API 인스턴스 | 인증, 인가, 모든 도메인 로직, 스케줄 작업 2종 | 상태를 로컬에 두지 않는다. 세션도 Redis에 있으므로 어느 인스턴스로 요청이 가도 결과가 같다. |
| MySQL | 모든 데이터의 원본(source of truth) | 테이블 구조는 애플리케이션이 만들지 않는다(검증만 함). 스키마 원본은 `api/db/schema.sql`이다. |
| Redis | 세션 저장소, 쿠폰 발급 선착순 판정, 조회수 버퍼 | 잃어도 되는 데이터와 DB로 다시 만들 수 있는 데이터만 둔다. 쿠폰 발급 결과의 원본은 MySQL이다. |
| GCS | 상품 이미지 저장, 공개 URL 제공 | 클라이언트가 서명 URL로 직접 업로드한다. API는 객체의 존재와 메타데이터만 확인한다. |
| 관리 포트 :8090 | `health`, `prometheus`만 노출, 인증 없음 | 외부 접근은 인프라 방화벽으로 막는다. 애플리케이션은 이 포트를 막지 않는다. |
| 배포 | GitHub Actions(수동 실행) → Artifact Registry 이미지 → GCE Managed Instance Group 전체 교체 | 무중단 배포가 아니다. 모든 인스턴스를 동시에 교체한다(`max-unavailable=100%`). |

테이블 관계와 핵심 제약(유니크, FULLTEXT)은 [README의 ERD](../README.md#erd)에, 컬럼 전체는 `api/db/schema.sql`에 있다.

## 애플리케이션 내부 모듈

패키지는 도메인 단위로 나뉘고, 각 패키지 안은 `controller → service → repository → entity` 계층을 따른다. 모듈마다 맡는 일은 루트 `CLAUDE.md`의 프로젝트 구조와 각 모듈의 `CLAUDE.md`에 있다. 모듈 사이의 의존은 코드에서 확인한다(서로 참조하는 모듈이 여럿 있다).

## 대표 흐름: 주문 생성 (`POST /api/orders`)

1. **보안 필터**: Redis 세션에서 인증 정보를 복원하고, CSRF 토큰을 검증하고, `BUYER` 역할인지 확인한다. 하나라도 실패하면 컨트롤러에 도달하지 못한다.
2. **요청 본문 검증**: 컨트롤러 인자를 바인딩할 때 본문을 검증한다(멱등 키 검증보다 먼저).
3. **멱등 래퍼**: `Idempotency-Key` 헤더 형식을 검증한 뒤, 요청 본문으로 지문(SHA-256)을 만든다.
4. **트랜잭션 1 (별도)**: `(user_id, scope, key)`로 멱등성 record를 찾는다.
   - 기록이 없으면 `PROCESSING` 기록을 저장하고 즉시 커밋한다.
   - 기록이 있으면 재응답, 409, 또는 만료 기록 삭제 후 재선점 중 하나로 끝난다.
   - 같은 요청이 동시에 들어와 유니크 제약에 걸리면 이 트랜잭션을 한 번 더 시도한다.
5. **트랜잭션 2 (별도)**: 아래를 모두 한 트랜잭션에서 처리한 뒤 멱등성 record를 `SUCCEEDED`로 바꾼다.
   1. 구매자 조회
   2. 장바구니 항목 일괄 조회(상품·카테고리·판매자·썸네일 fetch join). 중복 ID, 없는 항목, 삭제된 상품이 있으면 거절한다
   3. 쿠폰 일괄 조회(`SELECT … FOR UPDATE`)
   4. 할인 계산과 쿠폰 사용 처리
   5. 재고 조건부 차감(JDBC 배치, `product_id` 오름차순)
   6. 주문·주문항목 insert(cascade)
   7. `product_stat.order_item_count` 증가(JDBC 배치, `product_id` 오름차순)
   8. 쿠폰 사용 스냅샷 insert
   9. 장바구니 항목 삭제 또는 수량 차감(항목 ID 오름차순)
6. 트랜잭션 2가 예외로 롤백되면, 세 번째 별도 트랜잭션에서 `PROCESSING` 기록을 지워 같은 키로 재시도할 수 있게 한다.

주문 생성과 취소가 `inventory`와 `product_stat`에 락을 거는 순서는 서로 같아야 한다. 과거에 이 순서가 달라서 데드락이 났다.

## 스케줄 작업 (모든 인스턴스에서 동시에 실행됨)

| 작업 | 주기 | 여러 인스턴스가 동시에 돌 때 안전한 이유 |
|---|---|---|
| 쿠폰 이벤트 캐시 적재 | 이전 실행이 끝나고 30초 뒤(`fixedDelay`) | 활성 상태이고 시작 10분 전부터 종료 전까지인 이벤트를 Redis에 올린다. Lua 스크립트가 "meta 키가 없을 때만" 초기화하므로 한 번만 적재된다. 이벤트를 만들 때 이미 열린 이벤트이면 그 자리에서 바로 적재한다. |
| 조회수 반영 | 이전 실행이 끝나고 30초 뒤(`fixedDelay`) | Redis dirty set에서 `SPOP`으로 상품 ID를 꺼내므로 인스턴스끼리 나눠 가진다. 청크 크기와 1회 최대 청크 수는 설정값이다. |

분산 락이나 별도 워커는 없다. 스케줄 작업을 새로 추가할 때도 여러 인스턴스에서 동시에 실행돼도 결과가 같게 만들어야 한다.

## 경계에서 오가는 것과 오가지 않는 것

- **클라이언트 ↔ API**: JSON 본문, 세션 쿠키(`SESSION`), CSRF 헤더, `Idempotency-Key` 헤더가 오간다. 이미지 바이트는 오가지 않는다.
- **API ↔ GCS**: 서명 URL 생성, 객체 메타데이터 조회만 한다. 업로드와 다운로드는 클라이언트가 GCS와 직접 한다(버킷이 공개 읽기라고 가정).
- **API ↔ Redis**: 세션은 Java 직렬화 객체로 저장한다(주의점은 auth 모듈 문서). 쿠폰 캐시와 조회수 버퍼의 키는 coupon과 product 모듈 문서에 있다.
- 결제, 배송 추적, 메시지 큐, 외부 알림은 연동하지 않는다.
